# 剪辑方法：画面增量、设计规则、动作对点与经验回写

版本：1.1 ｜ 2026-09-30 ｜ 1.1 变更：记录主理人对待定事项的决定 ｜ 来源见 [SOURCES.md](SOURCES.md) 第 6 节。本文只收录对照本项目形态后采纳的做法；执行规则的摘要在 `AGENTS.md` 第 6、9、10、11、15 节，细则以本文为准。

## 1. 参考来源与形态差异

参考视频来自创作者「桌子的频道」，讲的是他用 Agent + Remotion 做视频的完整流程（本地文件 `微信视频2026-09-29_230919_843.mp4`，7 分 31 秒）。画面里出现了他的 `AGENTS.md`、`DESIGN.md`、制作大段表、专项经验页和复盘提示词。视频中提到的公开仓库 Table-VideoSOP 本次没有访问，下文只依据视频画面和口播。

两边形态不同，搬用时要区分：

| 维度 | 参考视频 | 本项目 |
|---|---|---|
| 画面主体 | MG 动画 + IP 角色 + 生视频，逐段定制 | 真实录屏作证据，Remotion 场景模板由数据驱动 |
| 渲染方式 | 各段独立目录、多个对话并行制作后拼接 | 单一 `timeline.json` 一次渲染 |
| 人物 | 固定 IP 形象 | 默认不出镜，没有 IP 形象 |

因此只采纳与画面形态无关的方法：画面增量、设计规则的建立程序、先样片后整段、动作对点、开场单独打磨、封面参考、制作复盘。

## 2. 核心思想

时间码为参考视频中的大致位置。

1. **画面给配音做增量，不复读**（3:22–3:36）。画面是用来增强配音表达的；整段画面只是把配音文字再显示一遍、让字飞来飞去，就和做 PPT 没有区别。
2. **按配音拆制作段，每段先答三问**（3:08–3:20）：声音已经说了什么，画面要补充什么，屏幕上真正需要留下的信息是什么。他的制作大段表列为：段 ID、口播范围（SRT 序号与时间）、叙事任务、声音已经提供、画面必须新增、必须上屏文字。
3. **规则分层，按任务路由**（1:02–2:48）。`AGENTS.md` 管两件事：做什么任务时读哪份经验，以及常见注意点。`DESIGN.md` 管画面长什么样，SOP 管制作顺序。专项经验页只在命中任务时读取。单期的构图、帧数和时长只作参考，不能变成系列默认参数。
4. **设计规则自己定，用两个测试定出来**（1:23–2:36）。设计规则决定片子有没有自己的味道，不能交给模型默认。静态测试定外观，动态测试定运动。
5. **先出设计与样片，再做整段**（4:37–4:58）。不让 Agent 直接跑整段成片：先出整段设计图和动画标注，人初审后再做；涉及连续状态转换的复杂画面，先做几秒样片。
6. **动作打点，音效对点**（1:13–1:18、5:27–5:37）。做动画时记下关键动作的时间点，配音效时直接对点。
7. **开场单独打磨**（4:59–5:25）。开场也是一个制作段，但单独设计，要更抓眼球。
8. **做完必复盘，把新坑写回规则**（6:03–6:23、7:25–7:30）。每次制作都可能遇到新问题，沉淀下来后面才越做越顺。
9. **只在锁定的时间线上做内容**（6:26–6:49）。流程以最初的配音为基准；时间线一动，后面的动画、音效、字幕都要重新对齐，相关画面要重渲染，让 Agent 来回改很耗 token。这套流程不适合频繁调整剪辑结构。

## 4. 采纳细则

### 4.1 画面增量三问

进入画面制作前，每个镜头的 `purpose` 按三问写清：

| 问题 | 写在哪里 | 要求 |
|---|---|---|
| 口播已经说了什么 | `segment_ids` 指向的语段 | 不必重复抄写，引用即可 |
| 画面在口播之外新增什么 | `purpose`，在原有作用标签后追加，例如「成品展示｜新增：规范后标书的真实页面」 | 至少一种：证据（录屏结果、输出文件、前后对比）、动作（真实操作过程）、关系（流程、因果、对比、层级）、位置感（全局到局部） |
| 屏幕必须留下什么 | 场景 `params` 中的文字（标题、要点、注释等） | 只留关键词、数字和结论；字幕已承载口播全文，画面文字不逐句复制 |

「新增」一栏写不出来时，先改为证据或动作；实在没有就缩短该镜头，或与相邻镜头合并。先决定这个镜头为什么存在，再决定它长什么样。

### 4.2 设计规则（`DESIGN.md`）的建立程序

`docs/DESIGN.md` 记录系列的视觉与运动语言：颜色、字体层级、卡片圆角与阴影、背景、强调方式、运动性格、转场和音效风格。风格由账号主理人拍板，执行者不自行决定；该文件建立前沿用 `remotion-render` 现有主题。

**静态测试，定外观。** 先从 Dribbble、Pinterest、Behance 等设计网站找 2～3 张参考图，只作风格参考、不入片。用同一个镜头的内容渲染几个变体（背景色、圆角、卡片密度、强调色），并排比较，再口头微调。本项目可以用 `remotion-render` 的审片静帧对同一时间轴出多套主题静帧。

**动态测试，定运动。** 以迪士尼动画 12 原则为检查词，模型能理解这套术语。重点看：

- 预备（蓄力）与惯性：动作开始前有没有准备，停下时有没有自然减速。
- 形状连续变换：例如一个方块能否连续变成一台电脑，而不是淡出后淡入。
- 元素交互：例如小球撞到另一个图形，目标有没有真的被带动。
- 跟随与次要运动：主体停下后，附属元素是否稍晚停下。
- 挤压与拉伸：有没有用，用得是否过度。

不喜欢弹跳感强的传统图形动画时，可以直接拿喜欢的运动视频让模型拆解运动参数，再按拆解结果复测。本项目是 AI 实战内容，清晰优先：运动服务于指向和因果，不能抢录屏证据。

两项测试都满意后写入 `DESIGN.md`：记录选择、理由和样例静帧路径；具体数值落到 `remotion-render` 的主题代码，两处同步。

**分层原则。** `DESIGN.md` 管系列，本文与各技能 `SKILL.md` 管方法，单期 `shots.json` 与 `timeline.json` 管具体内容与时间。单期镜头的构图、帧数和时长只作参考，不回写为系列默认参数。

### 4.3 先设计、后整段

- 正式渲染前，先出每镜关键帧静帧自查：画面增量是否成立、字幕是否挡住关键内容、是否越出安全区。
- 连续状态转换、多元素交互或新组件，先渲染该镜头几秒样片，确认难点可行再合入整片。样片只验证真正的难点，不因为句子多、状态多就机械增加样片。
- 已确认且条件未变的镜头保持锁定，不借返工顺手重做。

### 4.4 动作标记与音效对点

- 动作标记以镜头起点 `00:00.000` 为基准，标注主要动作的触发、开始、接触或碰撞、状态变化、结束和停稳时间。不能只写「快一点」「先后出现」这类相对描述。
- 时间按毫秒显示，工程计算保留帧精度。局部帧 `f` 与全片帧 `F0 + f` 分开写，局部秒点 = `f / fps`，不得混用。Remotion 镜头的动作时间取自组件帧常量与时间轴起点，由程序换算，不手估。
- 单次音效写精确时间点，例如 `SFX @ 00:01.250`；持续声写起止区间，例如 `00:01.250–00:02.100`，并注明声源、对应动作和声音含义。不写「这里加音效」「与动作同步」这类无法对点的描述。
- 录屏、生成视频或素材剪辑定稿后，按实际选用的片段重新校准动作与音效时间。
- 任何变速、截短、补帧、延长或镜头起点调整，都要在进入音效制作或最终合成前同步更新动作与音效标记；没有重新校准的旧时间点不得交给混音。
- 人声、音效、配乐的相对电平在首个配乐项目中定下，写入 `av-export` 配置。
- 动作标记与音效参数的正式数据字段推迟到第一个使用音效的项目再定，见第 6 节。

### 4.5 开场单独打磨

开场作为独立镜头组规划和制作，仍受 AGENTS 第 6 节的开场规则约束。

1. 脚本阶段出至少两版开场方案，每版包含首句与前 3～10 秒的画面。
2. 首版默认不采纳：先要求模型逐条指出首版的弱点（是否 3 秒内出现成品、是否点名具体人群、画面是否只是文字飞入），再出第二版。从第二版起认真比较。可在推理强度更高的模型或会话里做。
3. 选定的方案整理为镜头说明（`shots.json` 条目与场景参数）后再制作；有问题时给出具体改进方向，打回重做。

### 4.6 封面

每期准备两张参考图：一张定画风，一张定构图。记录来源，只作参考不入画面。按平台分别出封面方案（底图提示词与排版层文字），准确文字由排版层绘制。

### 4.7 配音前朗读

配音前主理人把 `voiceover.txt` 朗读一遍，读不顺、拗口、断句不清的句子先改稿再配音。这一步并入脚本定稿确认，不新增确认点。参考视频的作者认为「去 AI 味」类写作技能对他的文案没有作用；本项目继续用 `human-writing` 改口播，是否有效以朗读结果判断。

### 4.8 制作复盘与经验回写

与 AGENTS 第 15 节的平台数据复盘分开进行。

- **时机**：一段实质返工结束后，或整期交付后。
- **输入**：真实文件与证据，包括 `project.json`、各平台 `shots.json` 与 `timeline.json`、`qa/report.json`、返工前后的文件差异，以及记录下来的主理人原话。不凭模糊回忆。
- **执行**：按 [`templates/production-retro.md`](../templates/production-retro.md) 进行，输出 `projects/<项目>/retro/production-retro.md`。
- **纪律**：
  - 保留主理人原话，写清问题层级、返工轮次和解法。
  - 判断是「规则没写」还是「写了没执行」。写了没执行的，改触发入口（在哪一步、读哪份文件时应当看到），不新增条文。
  - 需要写入的规则保留正反两面：该怎样，不该怎样。
  - 未验证的想法单列为候选，不写成经验。
  - 通用方法、系列视觉偏好和本期特例分开；单期参数不升级为默认。
  - 列出本期没用上或造成负担、可删减合并的规则与检查；已有相同条目时修改原条目，不新增重复规则。
  - 只提交修改建议；主理人选定后再改规则与技能，并检查受影响的引用。
- **经验落点**：通用方法写入 `AGENTS.md` 或本文，系列视觉写入 `docs/DESIGN.md`，环节工具的坑写入对应技能的 `SKILL.md`，本期特例只留在项目复盘里。

### 4.9 时间线边界

本流程以定稿配音为时间基准，只适合在锁定的时间线上做内容。增删段落、调换顺序这类结构调整，在配音定稿前完成。定稿后再改结构，按 `docs/DATA_CONTRACTS.md` 第 7 节失效重算，并先估算重渲染范围和费用。需要反复试剪结构的内容，先在可视化剪辑软件里粗剪、定下结构，再进入本流程。

## 5. 未采纳及原因

| 做法 | 不采纳的原因 |
|---|---|
| 每段一个独立目录、开多个对话并行制作 | 与 AGENTS 第 4 节「共享清单由一个执行者写入」冲突；本项目由单一时间轴渲染，分段并行收益小。开发新场景组件时，仍在 `remotion-render` 技能内单独开发和测试 |
| 用生视频展示 IP 形象 | 本账号默认不出镜、没有 IP 形象；生视频按 AGENTS 第 9.2 节只用于录屏和组件都表达不了的镜头。是否建立 IP 形象属于账号定位决定 |
| 参考视频所用工具：ChatCut（可视化时间线粗剪、剪配音、出字幕）、HyperFrames、Recordly（开源录屏，自带缩放动画）、Google Flow（生视频）、ChatGPT 网页生图 | 均未核验，不进入 WORKFLOW 工具表。Recordly 可作为录屏模式（`footage` / `hybrid`）接入时的候选之一，接入前核验许可、系统支持和导出格式 |
| 用 Computer Use 操作剪映、达芬奇 | 作者自述 token 消耗和完成度仍在测试，Windows 下不能后台操作；暂不跟进 |

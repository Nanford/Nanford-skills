# 阶段 7 门禁细则

图文成品须同时按 `visual-layout.md` 查看最终 PDF 的每一页并记录检查结果：标题条、正文框与表格及组图边线是否对齐，跨页续框是否清楚，正文和图题是否可检索。图片/图片清单构建后发生变化会触发 B3，必须重新检查和出稿；成功的属性校验不能代替图内工程内容与页面效果核查。

阶段 6 完成后读。阶段 7 对成品 `output/施工组织设计.docx` 跑一遍全部门禁（B1～B13、W1～W10），逐条处理命中，和用户逐行核对初步评审表，最后出门禁报告。门禁只做检查，不出分数。各项定义见 `references/gate-catalog.md`。

DOCX 放行后，按 `pdf-delivery.md` 导出并逐页检查完整 PDF，核对 PDF 与当前 DOCX 的对应关系。DOCX 门禁报告通过只证明 Word 通过检查，交付时还须核对 PDF 的检查记录。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。命令在哪个目录运行都可以。所有材料只在本机处理，不外传（R26）。

## 一、前提：阶段 6 完成

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 6
```

阶段 6 的完成条件，全部满足才能完成，否则脚本逐条列出：

- 阶段 5 的完成条件仍然成立：每项中间稿都已确认，确认后没改过；
- 成品在固定路径 `output/施工组织设计.docx`，旁边有同名的 `.build-report.json`；
- 构建报告是正式出稿，不是格式样张；出稿用的格式就是项目现在锁定的格式；
- 构建报告记下的来源正好是确认过的那版中间稿：各项一项不缺、按评审内容的顺序、每项只出现一次；
- 其他来源只能是 `实施方案/` 下 00 开头的封面、目录，排在最前，出稿后没改过；
- 成品的版式校验（不加 `--final`）没有阻断项。

第 4b-2 步之前出的稿，构建报告里没有来源的 sha256，须重新出稿。出稿后在 Word 或 WPS 里保存过成品，不影响阶段 6：保存后的成品由阶段 7 的 B3 在当前文件上查。

## 二、步骤

```powershell
#   1. 在 Word 或 WPS 里打开成品，更新目录和页码（全选后 F9，或右键"更新域"），保存，关掉
#   2. 文档属性里有作者、单位的（门禁 B5 会报），清掉；会留下备份，见第五节
python -X utf8 "<skill目录>/scripts/scan_docx_hygiene.py" <项目目录>/output/施工组织设计.docx --clean-properties
#   3. 全部门禁跑一遍，写门禁报告
python -X utf8 "<skill目录>/scripts/check_qingtian_final.py" <项目目录> [--office auto|word|wps]
#   4. 逐条处理命中（第四节），和用户逐行核对初步评审表（第六节），再跑第 3 步，直到可以完成
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --confirm-b12 <行号>
#   5. 完成前可以对定稿的成品做一遍类人评审预演（references/rehearsal.md），把薄弱点告诉用户；只是提示，不挡阶段 7
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录> --final --record <记录.json>
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 7
```

顺序固定为：**Word 保存 → 清属性 → 门禁**。任何一步改了成品（再在 Word 里存一次、再清一次属性），成品的 sha256 就变了。之前对成品记下的理由、初步评审对照的确认和门禁报告随之作废，从第 3 步重来。成品的预演记录也会显示要重做。中间稿的理由不受影响，它们锁的是中间稿。

运行门禁时成品不能在 Word 或 WPS 里开着。检查过程中成品被改动，脚本报错退出，不出结果。

## 三、一次运行查什么

`check_qingtian_final.py` 一次汇总以下内容，不改阶段状态：

| 门禁 | 查哪里 | 怎么查 |
|---|---|---|
| B1 | 整份中间稿；成品的一级标题 | 中间稿齐全、顺序照矩阵；成品里每项一级标题都在，与评审内容原文一致、顺序一致、不重复，没有别的一级标题（抓在 Word 里改过、删过、挪过的标题） |
| B2、W5 | 成品 | 计页，见 `stage-6-assembly.md` 第六节。同一份成品已有计页记录的直接复用，包括用户导出的 PDF 和人工页数，不会被又一次失败的自动计页覆盖；篇幅上限按当前规则卡重判。还没计页、上次又失败的，再试一次 |
| B3 | 成品 | 在当前成品上跑 `validate_docx_format.py --final`，阻断项逐条进门禁；提示只计数，细节见成品旁的 `.format-report.md` |
| B4、B7～B11、B13、W1～W4、W6、W7 | 各项中间稿 | 与阶段 5 自查相同，理由沿用 `review/gate-notes.json` |
| B5 | 中间稿正文；成品 | 正文查中间稿；文档属性、作者域、封面目录、页眉页脚、图片名称、链接、文件名查成品；`output/` 下遗留的清理属性备份 |
| B6、W8 | 成品 | 隐藏内容、批注修订、嵌入和外部内容、面向评审系统的指令；评审端可能没有的字体 |
| B12 | 规则卡初步评审表 | 与施组有关的每一行都要用户逐行确认（第六节） |

每条命中前方括号里是十位编号，后面标出位置：成品、第 N 项中间稿、整份中间稿、初步评审表。T-暗标轨道 B5 阻断，其他轨道 B5 是提示（D3）。

结果写进 `review/gate-report.json` 和 `review/gate-report.md`，有阻断项时退出码为 1。

运行结果里还有一行类人评审预演的状态。它不是门禁：不算阻断或提示，不进门禁报告，不影响退出码。

## 四、命中怎么处理

处理原则与阶段 5 相同（决策 4a-1A），只是阶段 7 要把提示也处理完：

- **阻断项（B）** 清零。B4、B5、B7、B13 是脚本加人工复核的门禁：用户看过命中、明确说明这是误报和理由后，可以记下放行。其他阻断项只能改。
- **提示（W，以及非暗标轨道的 B5）** 逐条处理：改掉，或用户明确说明不改的理由后记下。gate-catalog："警告项逐条处理，或书面说明不改的理由"。
- 不能放行的命中，写了理由也不算：B1、B2、B3、B6、B8～B12，文档属性不为空、遗留的备份等标着"只能改"的 B5 命中，以及门禁前提缺失（如身份词清单格式不对）。
- 理由记在哪里，看命中的位置：

  ```powershell
  # 成品上的命中：记在 review/final-gate-notes.json，锁定成品的 sha256
  python -X utf8 "<skill目录>/scripts/check_qingtian_final.py" <项目目录> --dismiss <编号> --reason "<用户说明的理由>"
  # 中间稿的命中：记在 review/gate-notes.json，锁定那一项中间稿
  python -X utf8 "<skill目录>/scripts/check_qingtian_gates.py" <项目目录> --item <N> --dismiss <编号> --reason "<用户说明的理由>"
  ```

  用错了命令，脚本会指出该用哪个。不得替用户编理由，也不得为了过门禁劝用户放行。
- 改中间稿就要重新走阶段 5 的自查和确认，再重新出稿（阶段 6）。改完重新确认后的中间稿不再是成品出稿时用的那版，阶段 6 的条件随之不成立，脚本会提示重新出稿。
- 理由文件、门禁报告里都不存命中的原文和提示文字，B5 查到的名字不会落盘。具体内容只在运行脚本时显示。
- "人工核对"列出的项（没有数值可比的★条款、W4 只在本机比对等），由你和用户逐条对照原文核对。

## 五、清理文档属性留下的备份

`--clean-properties` 先把成品备份成 `output/施工组织设计.docx.clean-<时间>.bak`，再清属性。这份备份里还留着清掉的作者、单位。门禁把它报成 B5（只能改），其余命中都处理完后删掉，不要随标书交出去。

## 六、初步评审对照（B12）

初步评审一关过不了，施组没有分数（Q0）。规则卡初步评审表里 `tech_related` 为 true 的每一行（与施组有关的行），都要和用户逐行核对证据，用户明确认可后才确认：

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --confirm-b12 <行号>
```

行号是该行在规则卡初步评审表里的位置，从 1 起，与 `rule-card.md` 第三节的顺序一致。

核对时逐行对给用户：

- 该行的评审因素、评审标准原文，以及对施组的要求；
- 证据：格式校验（B3）、数值一致（B4）、★和实质性要求落点（B9）此刻有没有阻断，以及门禁运行列出的人工核对项；
- 施组里满足这一行的位置（如工期写在哪一项、数值是什么）。

确认的规则（决策 4b-3A）：

- 阶段 6 已完成、且条件仍然成立，才能确认；
- B3、B4、B9 还有阻断时不能确认：证据不成立，先改；
- 确认锁定此刻成品的 sha256 和初步评审表这一行。成品再保存过、这一行改过，确认作废，须重新核对；
- `tech_related` 为 false 的行不用确认；确认这种行，脚本拒绝；
- 只有用户明确表示认可这一行，才运行 `--confirm-b12`。用户没回、只说"差不多"，都不算认可。不得替用户确认。

B12 的命中不能用 `--dismiss` 放行，只能逐行确认。

## 七、门禁报告

`review/gate-report.json` 和 `review/gate-report.md` 记下这次运行：

- 成品的 sha256 和检查时间；
- 结论（能否完成阶段 7）和计数；
- 计页（方式、页数、篇幅上限）和格式校验的计数；
- 每条命中的门禁、编号、位置、级别、状态（未处理或已说明）和已说明的理由；
- 初步评审对照每行的状态；
- 人工核对项。

报告只记门禁、编号和位置，不记命中原文；具体内容运行脚本查看。成品再保存过，报告即作废，须重出。

## 八、完成阶段 7

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 7
```

以下全部满足才能完成，否则脚本逐条列出：

- 阶段 6 的完成条件仍然成立；
- 当前成品没有未放行的阻断项，也没有未处理的提示；
- 初步评审表里与施组有关的每一行都已确认，且确认后成品和规则卡都没变；
- 门禁报告是当前成品的，而且记的是这次放行的结果（报告出在处理完之前的，再跑一次 `check_qingtian_final.py`）。

完成条件不调 Word 或 WPS：这份成品还没计页的，按 B2 阻断报出来，先跑 `check_qingtian_final.py` 计页。

类人评审预演不是完成条件，没做也能完成阶段 7。

完成后可以做模拟自评（`self-score.md`），按招标文件的评分标准给当前成品模拟分，找失分点。它只评阶段 7 完成后的当前成品，不是阶段 7、8 的完成条件。成品再保存过、阶段 7 重开，模拟分就作废。

完成后进入阶段 8，见 `stage-8-submission.md`。阶段 8 完成时还会重新核对本节的条件：成品再保存过、规则卡改过还没重新确认、依赖改动那几行的确认已失效，阶段 8 都不能完成。

## 九、本阶段的硬停止

- 篇幅超上限，压缩会删掉评审内容要求的要点：停下来请用户取舍（B2）。
- 计页一直失败，用户也给不出 PDF 或页数：不跳过 B2，不估页数。
- 初步评审表某一行找不到满足的证据，或证据与原文对不上：停下来和用户核对，必要时回到阶段 2 改规则卡，不替用户确认。
- 用户要放行只能改的命中，或让你替用户编理由：说明决策 4a-1A，只改，不照做。
- 用户要在成品里加隐藏文字、写给评审系统看的提示语，或为躲检测故意改写：说明 Q13、Q10，不照做。
- 用户要预演给出分数、档次，或问成品能拿多少分：说明预演不出分数，本 Skill 不承诺分数，只列薄弱点；要模拟分的，阶段 7 完成后做模拟自评（`self-score.md`），说明它是模拟，不是青天的评分。
- 用户要在 Word 里改成品正文：说明改中间稿、重新确认、重新出稿的路径，不在成品上直接改内容（成品上的 B1 会拦下改过的标题，正文改动中间稿门禁看不到）。

# 类人评审预演

使用阶段：阶段 5 每项自查通过后、请用户确认前做一遍；阶段 7 门禁跑完后，对定稿的成品再做一遍。

预演只是提示：不是门禁，不挡确认，不挡任何阶段，不出分数和档次。用户说不做就不做。要分数的，阶段 7 完成后做模拟自评（`self-score.md`）。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。所有材料只在本机处理，不外传（R26）。

## 一、为什么要做

青天处理技术文件要走评审项解析、溯源解析、逻辑论述、评审建议几步（`hefei-rules.md` 第三节、第十节）。门禁能查数字、格式和关键词，查不出一段话能不能被找到、被摘出来、被写成给分的理由。预演就是让一个只看稿子的读者按前几步走一遍，把走不通的地方记下来。

评审建议这一步（出分数）预演不做。阶段 7 完成后可以做模拟自评（`self-score.md`），按招标文件的评分标准给模拟分。没有人见过青天的真实分数，那个分也只是模拟【推断】，不能当预期得分。

这套做法是根据公开规则做的【推断】，不是青天的真实逻辑，结果不能当成青天的判断。

## 二、谁来做，看什么

- **谁来做**：最好是新会话或子代理。写稿的会话知道自己想写什么，容易把稿子没写出来的内容脑补上去。条件不够时可以由写稿的会话自己做，记录里写"同一会话"，并告诉用户有这个盲区。
- **只给他看**：这一份稿子，加上规则卡里这一项的评审内容和档次原文。
- **不给他看**：事实卡、响应矩阵、写作思路。评委和青天手里都没有这些。

给子代理或新会话的提示可以这样写：

> 你在模拟评审者读一份施工组织设计的一项内容。下面是评审内容和档次原文，以及这一项的稿子。只根据这些材料，按三步记录走不通的地方：一，评审内容的每一点，能不能在稿子里找到响应；二，能不能摘出本项目事实、具体做法、量化指标、依据规范编号这四样可以直接引用的内容；三，要给这一项写充足的理由，哪里写不出来。不要打分，不要判断属于哪一档，不要改稿，不要编稿子里没有的内容。每条不超过 200 字，只写在哪里、缺什么。

## 三、三步

| 步骤 | 对应青天哪一步 | 怎么做 | 记到 |
|---|---|---|---|
| 1. 定位 | 溯源解析（Q2） | 评审内容的每一点，到稿子里找响应。找不到、散在别的地方、要翻很久才找到的，记下来 | `locate` 定位不到 |
| 2. 摘取 | 溯源解析、逻辑论述（Q3） | 从找到的响应里，摘本项目事实、具体做法、量化指标、依据（规范编号）。哪样摘不出，记下来 | `extract` 摘不出 |
| 3. 写理由 | 逻辑论述（Q3、Q4） | 按评审内容和最高一档的原文试写给分的理由（导则 2.2.2 要求评到 90% 以上的写明充足理由）。哪里只能说空话、写不下去，记下来 | `reason` 写不出理由 |

只记走不通的地方，不判断稿子够哪一档。

对成品做的时候，三步照走，再加两点，记到最接近的那一类：

- 同一项内容有没有散到别的项里（Q2）；
- 有没有哪一项明显比别的项薄（Q5）。

成品要先走完 Word 保存和清属性（`stage-7-gates.md` 第二节）。之后成品再保存过，记录就要重做。

## 四、怎样记录

把结果写成一个 JSON 文件，放在项目外或项目的临时位置都可以：

```json
{
  "reviewer": "子代理",
  "weak_points": {
    "locate": ["评审内容要求的成品保护，这一项里没有找到，只在质量措施一项提到一句"],
    "extract": ["第二段的垂直度控制有做法，没有量化指标"],
    "reason": ["工序衔接只写了原则，写不出针对本项目的理由"]
  }
}
```

`reviewer` 只能是 `同一会话`、`新会话`、`子代理`。三个列表都要有，没有就写空列表。

```powershell
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录> --item N --record <记录.json>    # 存第 N 项的预演
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录> --final --record <记录.json>     # 存成品的预演
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录> --item N                         # 看第 N 项的记录
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录>                                  # 看总览
```

存到 `review/rehearsal/NN.json` 和 `review/rehearsal/final.json`，锁定当时稿件的 sha256。稿件一改，状态变成"稿件已改要重做"。

脚本拒绝这些写法：

- 分数和档次判断，如"能拿 90 分""够得上优秀""优秀档""档次偏低"；
- 超过 200 字的条目（不把稿件原文贴进记录）；
- `reviewer`、`weak_points` 以外的字段，如 `score`。

`--check-item` 和 `check_qingtian_final.py` 的结果里各有一行预演状态，不影响它们的退出码和结论。

## 五、结果怎么用

- 薄弱点原文告诉用户，和中间稿一起看（`stage-5-writing.md` 第四节）。用户决定改不改，不改也不用说明理由。
- 要改的，补本项目的事实、做法、指标和依据。卡片里没有的回阶段 3 补卡，不编（R7）。
- 改了稿子要重新自查。要不要再预演一遍，由用户定。

## 六、不能做的

- 不写分数和档次，也不把预演结果说成"高分""稳了"。本 Skill 不承诺分数。模拟分在模拟自评里出，不写进预演记录。
- 不用官方评审系统试探打分（Q13；暂行办法第六条、第二十二条）。
- 不为了让预演找得到，就堆关键词或重复原文（Q6）。
- 不把稿件贴到网页版或其他在线工具（R26）。
- 不把预演当成用户确认。预演做过了，仍然要用户明确同意才能 `--confirm-item`。

## 七、局限

- 脚本只看做没做、稿子改没改，看不出预演做得好不好。
- 三个列表都是空的，可能是稿子没问题，也可能是没查出来。
- 同一会话做的预演有盲区，新会话或子代理也只是换了一个读者，不是青天。
- 高分能不能拿到，至今没有真实评审数据验证。

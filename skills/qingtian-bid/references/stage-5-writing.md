# 阶段 5 逐项撰写细则

阶段 4 完成后读。按确认过的大纲，一项评审内容写一个中间稿。每项按这个顺序走（R12），不跳项，也不提前写后面的项：

1. 写；
2. 自查；
3. 类人评审预演（只是提示，不挡确认，见第四节）；
4. 请用户确认；
5. 再写下一项。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。命令在哪个目录运行都可以。所有材料只在本机处理，不外传（R26）。

写作只用三样东西（R7）：

- 确认过的 `response-matrix.json`；
- 它引用的事实卡、资源卡条目；
- 规则卡。

不回头读公司原文件，也不读编目时提取的文字。

## 一、前提与步骤

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --start 5
#   写第 1 项：output/实施方案/01-<评审内容原文>.md                                 # 第二、三节
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --check-item 1    # 问题清零
#   做预演，存记录（references/rehearsal.md）；只是提示，用户说不做就跳过：
python -X utf8 "<skill目录>/scripts/rehearsal.py" <项目目录> --item 1 --record <记录.json>
#   请用户看第 1 项，用户明确同意后：
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --confirm-item 1
#   第 2 项起照样一项一项走，直到最后一项
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 5     # 第六节
```

以下任一条不满足，阶段 5 不能开始，已开始的也不能确认任何一项：

- 阶段 4 已完成；
- 大纲确认后没有变化；
- 资源卡没有缺口。

资源卡确认时有缺口（`outline_only`），整个阶段 5 都停在门外，不是有缺口的那几项才停（R8）。补齐公司资料，重新确认资源卡和大纲，才能开始。

## 二、中间稿的文件和结构

每项一个 Markdown 文件：

- 路径为 `output/实施方案/NN-<评审内容原文>.md`。NN 是矩阵序号，补足两位。
- 标题里有 Windows 文件名不许的字符（如 `/`、`:`）的，换成全角。
- `response-matrix.md` 的"中间稿"一列就是每项的文件名，照抄即可，与阶段 6 组装清单一致。

结构：

- **首行可见文字**是本项的一级标题 `# 一、工程概况`。序号用中文数字写进标题文字，标题照抄评审内容原文（R3、R4、R19）。框式版面在标题上一行加 `<!-- chapter-center -->`，并按招标文件调整对齐方式。
- **全文只有这一个一级标题**。下级标题从 `##` 起，编号也写进文字：`## （一）`、`### 1.`、`#### 1.1`。
- 版式标记（`<!-- pagebreak -->` 等，见 `build_response_docx.py` 头注释）可以放在标题前，不算正文。
- 图单独占一行，图片放在 `output/实施方案/images/`，写法见 `stage-6-assembly.md` 第四节。
- 图文施组先读 `visual-layout.md`。按确认样张，在中间稿用 `panel-grid-start/panel-end` 把章内标题条、成段正文、相关图表编成内容框；无框项目省略这组标记。工艺配图按 `image-generation.md` 发现可用能力、实际生成并逐图检查。图题、正文落点、依据和图片版本进入 `analysis/visual-assets.json`，关键参数仍须写在正文。

## 三、怎样写一项

动笔前先读矩阵里这一行：要点（`points`）、引用的事实、资源和★条款、预算页数。

**开头**

- 第一段直接回答本项评审内容：本项目怎么做，达到什么指标（Q2、W7）。
- 开头的针对性判断段写 3 句以上，点名本项目的事实，不写放之四海皆准的套话（R16）。

**每条措施写到四个要素**（Q3）：

1. 本项目事实；
2. 具体做法；
3. 量化指标；
4. 依据（规范编号）。

每项至少一组可考核的量化指标（R14、W2）。

**数字和名称**

- 工程量、面积、工期、节点、部位名称照事实卡和规则卡写，不换算，不改叫法（R15）。
- 同一个数字在各项之间一致（B4）。
- 施工总平面、临时设施、材料堆放、垃圾清运不与事实卡里的现场限制矛盾。补遗、答疑写明现场不具备或不允许设办公区、生活区、加工区、材料堆场的，不在现场布置，写场外怎么解决；场外安排事实卡和资源卡里都没有的，先问用户，不编（R7、R27）。

**资源**

- 人员岗位、机械、劳动力、物资只写资源卡里有的，数字照资源卡（R7、B10）。
- 人员只写岗位和持证类别，不写姓名、证书编号、电话、公司名称（Q12、B5）。

**★条款**：矩阵 `mandatory` 落在本项的条款，正文里写出满足它的做法，数值与条款原文一致（R5、B9）。条款登记了关键词的（规则卡视图里"正文须写到"），每个关键词照原文叫法写进正文（B9）。

**规范只引编号，不抄条文**（Q7、W4）。不整段套用模板或网络文本，也不故意造错来躲检测（Q10）。

**成段论述**

- 措施成段写，不写碎片清单，不做"措施控制表"（R16、W6）。
- 能做成表的只有：
  - 机械设备计划表、劳动力计划表、物资计划表；
  - 进度计划（横道图、网络图）；
  - 质量控制点表、危大工程清单、风险矩阵。
- 不用括号编号连续起段，一段内不堆叠多组括号（R20）。

**成品语言**

- 正文不写采购文件的章节号、条款号（R17）；
- 不写"根据招标文件要求""本节将"之类写作过程用语（R18）；
- 不残留 Markdown 符号（R19）。

**禁止项**

- 不写任何面向评审系统的指令性文字或隐藏文字（Q13、B6）；
- 只写一套方案，不并列"方案一、方案二"（Q14）；
- 不写报价、单价、费率、让利和任何金额，物资表、机械表也不列价格（Q0、B13）。招标文件给的投资额、应急资金额度确需写的，写之前问用户。

**重点难点一项**（招标文件把"重点、难点"列为评审内容，或把招标指定的内容落在本项）：

- 按招标文件列的重点难点逐条写，顺序照原文，每条一段：先说这一条在本项目里难在哪（点名事实卡里的部位、周边、工序），再写对策和量化指标；不另起招标文件没列的"重点难点"凑数（Q2、Q3）。
- 要求"补充完善危险性较大工程清单"的，在招标文件列的危大工程之后，按事实卡和工程量清单补上本项目实际有的，列成危大工程清单表（工程名称、部位、规模、是否超过一定规模、专项方案与论证安排），表后逐项写安全管理措施。招标文件写"/"的，照样按事实卡和工程量清单判断本项目有没有危大工程；判断不了的（如基坑深度、脚手架搭设高度事实卡里没有），先问用户，不猜（R7、R27）。
- 关键词照原文叫法写（B9）；与安全措施、施工方法两项重复的内容，在这里写到针对本项目的做法，别处引用不重抄（W4）。

**工期一项**："确保工期的技术组织措施"附总进度计划的横道图和网络图（hefei-rules.md 第八节【推断】）。

**篇幅**：按矩阵预算写。`--check-item` 会给出本项字数和预算字数【推断】，偏离超过 30% 的，在阶段 7 报警告（W5）。

## 四、自查与确认

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --check-item N
```

自查不改状态。它先查结构（决策 3c-3A）：

1. 撰写前提（第一节）；
2. 前面各项都已确认且仍有效；
3. 后面的项没有提前写；
4. 中间稿存在且不为空；
5. 第一行是本项的一级标题，全文只有一个一级标题。

再跑本项的内容门禁（第 4a 步，`check_qingtian_gates.py`），各项定义见 `references/gate-catalog.md`：

| 门禁 | 本项查什么 |
|---|---|
| B4 | 工期、开工竣工日期与规则卡、事实卡一致；资源卡上的人数、台数、物资数量照卡写（劳动力不超过高峰人数）。卡上没有参照值的，与其他各项比 |
| B5 | 身份词清单里的公司全称、简称、商标、网址；电话、8 位以上数字串、邮箱；"岗位＋姓名"。只查正文，文档属性和页眉图片在阶段 7 查 |
| B7 | 卡片里没有的地名（省市县镇乡）；带着本项目地名、却不在卡片里的"……项目/工程"；卡片里没有的"……有限公司/集团"。本公司名称归 B5 |
| B8 | 采购文件章节号、条款号；写作过程用语，包括【一手】【二手】【推断】标签；Markdown、HTML 和注释残留 |
| B9 | 落在本项的★条款：条款里的数值照原文写出；没有数值的，正文有一句同时写到条款的关键词和短语（如"质量标准""合格"） |
| B10 | 资源卡上没有的岗位、工种、机械写了人数台数 |
| B11 | 大纲把实施、进度或组织落在本项的，正文（含标题）写到 |
| B13 | 报价用语（投标报价、综合单价、下浮率、费率等）和金额（数字或大写数字加"元"、人民币、￥），表格也查；所有轨道都阻断 |
| W1～W4、W6、W7 | 引用的事实少于 2 条；没有量化指标；套话密度过高；规范条文写法、一段 3 个以上条文号、与别的项整句相同；碎片清单、括号堆砌、正文表格化；第一段没有直接回答本项 |
| W9 | 类别知识卡在本项的必备要点，确认过的矩阵里还留着，正文一个叫法都没写到（每项最多一条，合并列出；阶段 4 删掉的不查）；标题含"重点""难点"的一项不查。本项目确实不涉及的，请用户说明理由记下，不为凑关键词硬写 |
| W10 | 事实卡的现场限制禁止设的设施（材料堆场、加工区、办公区、生活区、室外堆放点），正文某句照写，没写不设或场外怎么解决（表格也查）。改成"现场不设……，……在场外解决"；确属误报的说明理由 |

B1（各项齐全、顺序照矩阵、没有多余的中间稿；00 开头的封面、目录不算中间稿，它们的身份泄露由阶段 7 的成品扫描查）和 B9 的整份落点（每条★条款都落在某一项）对全稿查：

```powershell
python -X utf8 "<skill目录>/scripts/check_qingtian_gates.py" <项目目录>             # 全稿
python -X utf8 "<skill目录>/scripts/check_qingtian_gates.py" <项目目录> --item N    # 只查第 N 项
```

数字比对只看正文段落，表格里按阶段列的人数、台数不比。W4 只在本机比对规范写法和各项之间的整句，查不到网络文本（R26）。B2、B3、B6、W5、W8、B12 要看成品 DOCX，在阶段 7 查（`stage-7-gates.md`）。

**身份词清单**：B5 要用户提供 `analysis/identity-terms.json`（模板 `templates/identity-terms.json`）。至少写一条本公司全称，可加简称、商标、网址后缀。不写人名，人名按"岗位＋姓名"另查。电话、证书号按格式另查，也不写。不读人员档案。没有这份清单时，B5 报一条提示（暗标轨道为阻断），请用户补上。

**命中怎么处理**（决策 4a-1A、4a-2A）：

- **阻断项（B）挡确认**。改稿后重新自查，清零才能 `--confirm-item`。
- B4、B5、B7、B13 是脚本加人工复核的门禁，可能误报。只有用户看过命中、明确说明这是误报和理由后，才记下：

  ```powershell
  python -X utf8 "<skill目录>/scripts/check_qingtian_gates.py" <项目目录> --item N --dismiss <编号> --reason "<用户说明的理由>"
  ```

  编号是命中前方括号里的十位编码。不得替用户编理由，也不得为了过门禁劝用户放行。
- 其他阻断项（B1、B8、B9、B10、B11）不能放行，只能改稿。门禁前提缺失的命中（如身份词清单格式不对）也只能补正。
- **警告项（W）不挡确认**，自查时列为提示，阶段 7 逐条改，或照上面的命令记下用户不改的理由。
- 理由记在 `review/gate-notes.json`，锁定当时中间稿的 sha256。中间稿一改，原来的理由作废，命中重新出现，需要用户重新判断。文件里不存命中的原文，B5 查到的名字不会落盘。
- 自查列出的"人工核对"（没有数值可比的★条款等）由你和用户逐条对照原文核对。

自查有阻断项时退出码为 1。

问题清零后，先做类人评审预演（`references/rehearsal.md`），再把中间稿给用户看。预演只是提示，不是门禁，不挡确认，不出分数和档次；用户说不做就跳过。说明五件事：

- 本项写到了矩阵里的哪些要点；
- 引用了哪些事实和资源；
- ★条款落在哪里；
- 还有哪些提示和人工核对项，已说明的误报、不改理由是什么；
- 预演记下的薄弱点原文，没做的就说没做。改不改由用户定。

只有用户明确表示同意，才运行 `--confirm-item N`。用户没回、只说"再看看"或提了修改意见，都不算同意。

确认时锁定三样东西（决策 3c-2A）：

- 中间稿本身；
- 矩阵里这一行；
- 这一行依赖的规则行、事实和资源此刻的内容。

## 五、改稿与失效

| 改了什么 | 哪些项失效 |
|---|---|
| 已确认的中间稿 | 只有这一项 |
| 矩阵的某一行（改后须重新确认大纲） | 只有这一行对应的项；其他行没变的项仍有效 |
| 某条事实、资源或规则行（改后须依次重新确认那张卡和大纲） | 依赖它的项（矩阵行没写 `cites` 的，规则卡任何一行变了都算） |
| 资源卡重新确认时有缺口 | 整个阶段 5 停下（R8） |

失效的项照第四节重新自查、请用户确认。

**按顺序**：确认第 N 项时，第 1 至 N−1 项都必须已确认且仍有效。

**不提前写**：后面的项有中间稿、却从没确认过，就是提前写了，挡住当前这一项的确认。删掉它或先挪走，确认完当前项再写。

**回头改前面的项**：后面的项确认过、后来失效了，不算提前写，不挡前面的项。改完前面的项，再依次重新确认后面失效的项。

**来了补遗或补了公司资料**：已完成的阶段从相应位置重开。规则卡、事实卡、资源卡和大纲依次重新确认，失效的中间稿逐项重新确认。

## 六、完成阶段 5

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 5
```

以下全部满足才能完成，否则脚本逐条列出：

- 资源卡没有缺口；
- 阶段 4 的完成条件仍然成立；
- 矩阵里的每一项都已确认，且确认后锁定的内容都没变。

阶段 6、7 的完成条件见 `stage-7-gates.md`，阶段 8 的见 `stage-8-submission.md`。

## 七、本阶段的硬停止

- 资源卡有缺口：只交大纲和缺口清单，不写正文，不"先按常规配置写上"（R8）。
- 写某项需要的事实或资源在卡片里没有：回阶段 3 补卡、重新确认，不在正文里编（R7）。
- 写着写着发现大纲要改（要点不对、★落点不对、页数不够）：先改矩阵，重新确认大纲，再写，不在正文里自行拐弯。
- 用户要求一次写完几项再一起看，或跳过某项先写后面的：说明 R12，不照做。
- 用户要求在正文里写人名、证书编号，或写给评审系统看的提示语：说明 Q12、Q13，不照做。
- 用户要放行 B1、B8、B9、B10、B11 的命中，或让你替用户编误报理由：说明决策 4a-1A，只改稿，不照做。
- 用户要预演给出分数、档次，或问这一项能拿多少分：说明预演不出分数，本 Skill 不承诺分数，只列薄弱点。
- 用户没有明确确认某一项。不得替用户确认，也不得在本项确认前写下一项。

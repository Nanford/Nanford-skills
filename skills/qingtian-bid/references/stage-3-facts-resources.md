# 阶段 3 事实卡与资源卡细则

阶段 2 完成后读。目标是三件事：

1. 本项目的事实逐条带出处，经用户确认（事实卡）；
2. 公司资源逐条指回公司资料文件，经用户确认（资源卡）；
3. 资料不全时，缺什么写清楚。有缺口的资源卡确认后，施组只许出大纲和缺口清单（R8）。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。命令在哪个目录运行都可以。所有材料只在本机处理，不外传（R26）。

两张卡都以 JSON 为准（决策 1A）：`analysis/fact-card.json` 和 `analysis/resource-card.json`。`project-facts.md` 和 `company-resources.md` 是脚本生成的视图，给用户看，不手改。

阶段 4、5 写机械、劳动力、物资和管理岗位，只引用 `resource-card.json`。不回头读公司原文件，也不读编目时提取的文字（R7）。

## 二、事实卡候选

`scaffold_facts.py` 读提取报告里状态为 `ok` 的三类文本：

- **招标文件**：依据记"招标文件"。
- **xlsx、xls 招标文件**：按工程量清单读，依据记"工程量清单"（xls 在阶段 1 已另存为 xlsx 再提取）。
- **用户声明的图纸、且提取得出文字的**（如设计说明）：依据记"图纸"。DWG、DXF 读出的文字也在内，出处写图号：图号一般在图框或图签块的属性里，同一个文件有多张图时，按文字所在的布局或图框对上图号，对不上的请用户看图确认。

阶段 1 没通过时，脚本直接拒绝（R9）。

它找三类东西：

- **标签取值**：建设地点、建设规模、建筑面积、结构形式、建筑层数、招标范围、计划开工日期、计划竣工日期。
  - 取值常跨行，按连续文本取到下一条条款编号或句号。
  - 招标文件没写的，再到图纸文字里找。
  - 每条的 `candidates` 列出全部命中的原文。公告和前附表写法不一时，由你对照。
- **清单分项**：从 xlsx、xls 清单里取编码、项目名称、项目特征、计量单位和工程量。空单元格先去掉再认，合并单元格导出的空列不影响。工程量后面的列不读，限价表登记成招标文件时，单价和合价也进不了候选。
  - 每一行先归类别知识卡（`boq` 的编码前缀和名称关键词，决策 5-5A）：先归场景卡（拆除、加固这类行编在哪个专业下都算改造），再归专业卡，最后归主类别卡。哪张卡都对不上的行算其他分项，比如只选了智能化卡时编在电气下的配管、桥架；其中按"项"计的是总价措施，不取。
  - 每张卡先保底 8 条，免得土建把安装、智能化挤掉。候选总数最多 150 条，保底取完还有名额的，剩下的行不分卡，其他分项也在内，一起取。
  - 取的时候按 6 位编码（分部分项）轮流，同组工程量大的在前，免得几十行门窗占满名额；同名分项只取第一次出现的。出处写"文件 工作表「表名」（提取文本第 N 行）"。
  - 没进候选的分项列在 `analysis/清单未进候选.md`，同名只列一次，每次运行重写。带编码却认不出单位或工程量的行也列在里面，只有编码和名称。看一遍，施组要用的照原件录入。
  - 这个取法是候选，不是判断：工程量大不等于造价高，也不等于施组该写。核实时对着清单，删掉不用的，补上要用的。
  - 规则卡还没定工程类别（阶段 2 没确认）时清单分项一条不取，确认规则卡后重跑。选到但卡片还没交付的类别，脚本在结果里列出，这些分项算在其他分项里。工程类别没有类别知识卡的项目，全部算其他分项。
- **补遗、答疑里的现场限制**：文件名含补疑、补遗、答疑、澄清、答复的招标文件里，含"严禁、不允许、不具备、禁止，以及紧邻、夜间、袋装、成品保护、深基坑、专家论证、交通疏导、交通封闭、全密闭、二次搬运、狭窄、临时用地、围挡、进场路线这类现场条件词"的整句（最多 20 条），类别记场地与周边。不是现场条件的（如只讲费用计入报价的）删掉。确认后的禁止类句子（不允许设办公区、严禁室外堆放等）阶段 4 的矩阵骨架拿来改写预填的控制点，阶段 5 的 W10 拿来比对正文，所以禁止的设施要照原文留着，不要改写成概括的话。
  - 例如"严禁在室外堆放""现场不具备且不允许设置办公区、生活区"。施工总平面和临时设施不得与之矛盾（阶段 5）。
  - 同一句只收一次，过长的截到 200 字，最多 15 条。招标文件正文里的"☑不允许""严禁工程转包"多是程序条款，不读。
  - 核实时删掉不是现场条件的句子。一句话里后半截讲费用、报价的（如"相关费用综合考虑在报价中"），只留现场条件那半句：施组不写报价内容（B13）。

以下内容脚本不取：

- 写着"见招标公告""符合……"的取值，以及合同格式里的空白处。
- 工期、质量标准、安全目标。这三项以规则卡为准，事实卡不重复。

项目里已有事实卡时，脚本不覆盖，候选另存为 `analysis/fact-card-候选-<时间>.json`，由你对照后手工并入。

候选只是线索。所有事实的 `checked` 都是 `false`，必须逐条回到原文核实。以下内容脚本做不了，要手工录入：

- **PDF 清单**：依据写"工程量清单"，出处写页码和清单编码。
- **读不出字的图纸**：依据写"图纸"，出处写图号（决策 2A）。
- **周边环境、地质水文、技术要求**等没有固定标签的事实。

## 三、核实与填写事实卡

每条事实写成：

```json
{"id": "F07", "category": "工程量", "text": "010502001001 矩形柱 混凝土强度等级：C30 m3 128",
 "quantity": {"item": "矩形柱", "amount": 128, "unit": "m3"},
 "basis": "工程量清单", "source": "工程量清单.xlsx 工作表「分部分项」（提取文本第 3 行）", "checked": true}
```

| 键 | 写什么 |
|---|---|
| `id` | F01 起编号，不重复。阶段 4 响应矩阵按编号引用 |
| `category` | 规模与结构、招标范围、场地与周边、工期与节点、工程量、技术要求、其他，七选一 |
| `text` | 事实原文。数值、单位、编号照原文，不换算，不概括 |
| `quantity` | 工程量事实必填：`item`（项目名称）、`amount`（正数）、`unit`（照原文单位） |
| `basis` | 招标文件、工程量清单、图纸、用户提供，四选一 |
| `source` | 出处：文件、页码或工作表行号；补遗写补遗编号；图纸写图号 |
| `checked` | 核对原文后改为 `true` |
| `cites` | 这条事实依赖规则卡的哪几行，写法见下 |

**`cites` 怎么写**（决策 D9-1A）：

- 写规则卡的行键：列表行写编号（`M01`、`KD01`、`PR01`、`S01`、`S01-1`），评审内容写序号（`review_items.3`），单值字段写字段名（`schedule`）。写了规则卡里没有的行键，校验不过。
- 和规则卡无关的写 `[]`。骨架给清单分项预填了 `[]`，其余事实核实时填。
- 没写的，规则卡任何一行变了都要重新确认。

- **规模与结构必须有**：至少一条"规模与结构"类的事实，写明规模和结构形式。
- **补遗优先**：补遗改过的事实，取补遗的值，出处换成补遗。不得两个值并列。
- **用户提供**：事实只能由用户口头或书面提供的（如现场踏勘所见），依据写"用户提供"，出处写谁在何时提供。
- `candidates` 核实完可以删，留着不影响校验。其他键一律不收。

## 四、公司资源编目

```powershell
python -X utf8 "<skill目录>/scripts/index_materials.py" --project <项目目录>
python -X utf8 "<skill目录>/scripts/index_materials.py" --project <项目目录> --show "<编目路径>"
```

编目的范围是项目状态里登记的公司资源资料：建项目时自动登记的项目 `公司资料/`，开工时的 `--resources`，以及开工后用 `project_status.py --add-resource <路径>` 补登的文件或文件夹。都原地编目，脚本不复制。项目里的路径记相对路径，项目整体搬走也能编目。两处登记里编目路径相同的文件（比如两个 `公司资料/机械设备/` 下同名的表），资源卡分不清指的是哪一个，编目报错，请用户改一个名字。

编目前先看 `project_status.py <项目目录>` 的概览：`资料文件 0 个` 说明还没放资料，先请用户按 `公司资料/` 各目录的说明放进去，不要先跑编目出一张全是缺口的资源卡骨架（资源卡已存在时，重新编目不会覆盖它，缺口要手工删）。

**分类**：按编目路径（从登记的文件夹名起算）的关键词，分成管理岗位与持证、机械设备、劳动力、物资、其他五类。路径里有人员、证书、花名册等字样的，一律按人员资料处理。文件名（不含扩展名）以"证"结尾的，比如操作证、职称证、安全生产考核合格证，不管放在哪个子目录也按人员资料处理，防止放错目录把证件文字存进项目。代价是材料合格证、供应商资质证这类不涉及个人的证件也不提取文字，按原文件或 `--show` 核对。

**产出**：

| 路径 | 内容 |
|---|---|
| `analysis/material-index.json`、`.md` | 每个文件的编目路径、类别、sha256、文字提取状态 |
| `analysis/resource-text/<文件名>.txt` | 机械、劳动力、物资和其他类文件的文字，供核对 |
| `analysis/resource-card.json` | 资源卡骨架，只在项目里还没有资源卡时生成。某类一个文件都没有的，先在 `gaps` 写一条缺口 |

**人员资料不落盘**（决策 3b-1A）。花名册、证书等人员类文件只记编目信息，不把文字存进项目：

- 核对时看原文件；
- 或用 `--show` 把一个文件的文字临时打到屏幕上，不保存。

文字提取状态只供参考。表格文件字少会显示 `needs_ocr`，照片和老格式会显示 `failed`，都不阻断编目。资源卡按原文件核对。

资料空壳不按文件数判。资源卡逐条指回编目里的文件，缺什么写进 `gaps`。文件数够，不说明资料够。

## 五、填写资源卡

资源卡分四节。每节一个列表，每条带编号、内容和出处：

| 节 | 编号 | 内容键 | 必填 |
|---|---|---|---|
| `managers` 管理岗位与持证 | P01 起 | `role` 岗位、`count` 人数、`cert_category` 持证类别 | 全部 |
| `machinery` 机械设备 | E01 起 | `name` 名称、`model` 型号、`count` 台数、`ownership` 自有或租赁 | `name`、`count` |
| `labor` 劳动力 | L01 起 | `trade` 工种、`peak_count` 高峰人数、`phases` 投入阶段 | `trade`、`peak_count` |
| `materials` 主要物资 | S01 起 | `name` 物资、`quantity_fact` 或 `quantity`、`supply` 供应方式、`batches` 进场批次 | `name`、数量、`supply`、`batches` |

人数和台数写正整数。

```json
{"id": "P01", "role": "项目经理", "count": 1, "cert_category": "一级注册建造师（建筑工程）",
 "basis": "公司资料", "file": "公司资料/项目管理人员/项目部管理人员配置表.xlsx", "locator": "Sheet1 第 2 行", "checked": true}
{"id": "S01", "name": "商品混凝土", "quantity_fact": "F07", "supply": "就近商品混凝土站供应",
 "batches": "按浇筑计划分批进场", "basis": "用户确认", "source": "用户 2026-10-28 确认", "checked": true}
```

**出处**，二选一：

- `公司资料`：`file` 写 `material-index.md` 里的编目路径，`locator` 写在该文件里的位置（页码、工作表和行号）。管理岗位、机械和劳动力只能写这一种（R7、R8）。
- `用户确认`：只用于数量取自工程量清单的物资（决策 3b-2A）。供应方式和批次由用户确认，`source` 写谁在何时确认。

**只记岗位，不记人**（决策 3b-1A）：

- 资源卡只收上表列出的键、出处键和 `cites`。姓名、证书编号、身份证号、电话等一律不收。
- 内容里出现 8 位以上的连续数字，按疑似证书编号或电话拦下。
- 施组里写人员，也只写岗位和持证类别（Q12）。

**物资数量**（决策 3b-2A），二选一：

- 清单里有的物资，`quantity_fact` 写事实卡里那条工程量事实的编号，数量取清单原值，不另写。
- 周转材料等清单外物资，`quantity` 写 `{"amount": 60, "unit": "t"}`，出处必须是公司资料。

**依赖**（决策 D9-1A）：`cites` 写这条资源依赖规则卡的哪几行、事实卡的哪几条，行键的写法见第三节，事实写编号（`F07`）。都不依赖的写 `[]`。没写的，规则卡或事实卡任何一行变了都要重新确认。`quantity_fact` 引用的事实不用再写。

**缺口**：`gaps` 每条写成 `{"section": "labor", "text": "劳动力计划只有工种，缺分阶段人数，请用户补充"}`。

- 某一节一条都没有时，必须有该节的缺口。
- 资料不够就写缺口，不得为了凑齐编造（R7）。
- 补齐后删掉对应缺口，重新校验确认。

## 六、请用户确认

先运行 `--check`，问题必须清零（退出码 0）。然后把视图给用户逐节说明：

- **事实卡** `project-facts.md`：
  - 规模与结构、招标范围、场地与周边；
  - 工程量清单的主要分项和数量；
  - 哪些事实是手工录入的，依据是什么。
- **资源卡** `company-resources.md`：
  - 每节的条目和出处；
  - 物资数量引用了哪条清单事实；
  - 缺口清单，以及有缺口时只许出大纲。

只有用户明确表示同意，才运行 `--confirm`。用户没回、只说"再看看"或提了修改意见，都不算同意。

以下情况确认会被拒绝：

- 阶段 2 未完成；
- 事实卡：规则卡未确认或已失效；
- 资源卡：规则卡或事实卡未确认或已失效；
- 校验还有问题。

确认时一并锁定卡片依赖的内容。失效按行算（决策 D9）：上游变了，只有依赖那一行的行失效，`project_status.py <项目目录>` 显示原因和涉及哪几行。有行失效时卡片不再算已确认，阶段 3 不能完成：

| 卡片 | 锁定的内容 | 什么情况会失效 |
|---|---|---|
| 事实卡 | 事实卡自身；每行 `cites` 写的规则行 | 改了事实卡；引用的规则行变了（没写 `cites` 的，规则卡任何一行变了） |
| 资源卡 | 资源卡自身；登记的资源路径和编目里每个文件；每行 `cites` 写的规则行和事实，物资的 `quantity_fact` | 改了资源卡；补登资源、公司资料文件被改动；引用的规则行或事实变了（没写 `cites` 的，规则卡、事实卡任何一行变了） |

**有缺口时也能确认**，确认记录里写 `outline_only: true`。阶段 4、5 只出大纲和缺口清单，不写资源数字，直到缺口补齐、重新确认（R8）。

**确认后要改**：改 JSON，再 `--check`，请用户看改动的地方，用户同意后再 `--confirm`。上游卡片改了，下游受影响的行也要按新内容重新确认；重新确认后内容没变的行，不连累它下面的行。

**来了补遗**：按 `stage-1-extract.md` 第三节登记。已完成的阶段 1 起全部重开，规则卡、事实卡、资源卡依次重新核对确认。

**补了公司资料**：

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --add-resource <文件或文件夹>
```

路径必须存在，原地登记，不复制。已完成的阶段 3 起重开。之后重新运行 `index_materials.py --project`，资源卡已存在，不会被覆盖；按新资料补条目、删缺口，再确认。

## 七、完成阶段 3

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 3
```

以下全部满足才能完成，否则脚本逐条列出：

- 规则卡、事实卡、资源卡都已确认，且确认后锁定的内容都没变；
- 资源卡按当前校验规则复核仍然通过。

资源卡有缺口时，阶段 3 照样可以完成，概览显示"有缺口：只许出大纲和缺口清单（R8）"。

完成后读 `stage-4-matrix.md`，开始写响应矩阵。

## 八、本阶段的硬停止

- 必需的事实在招标文件、清单和图纸里都找不到，或者几处写法互相矛盾（如公告和前附表的建筑面积不同）：问用户，不猜。
- 用户要求把姓名、证书编号写进资源卡：说明决策 3b-1A，不照做。人员名单和证书属于商务文件（项目管理机构），由用户另行编制，本版本暂不生成。
- 用户要求在没有公司资料的情况下"先按常规配置写上"：说明 R7、R8，只写缺口，不编造。
- 用户没有明确确认事实卡或资源卡。不得替用户确认，也不得在资源卡确认前写资源数字（R8）。

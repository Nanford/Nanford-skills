# 阶段 2 解标定轨细则

阶段 1 完成后读，开始前先读 `hefei-rules.md`。目标是三件事：

1. 规则卡逐字段对照招标文件原文核实，经用户确认；
2. 评审轨道按招标文件判定；
3. 招标文件的格式规定覆盖开工所选，经用户确认。

规则卡确认前不写正文（R1）。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。命令在哪个目录运行都可以。所有材料只在本机处理，不外传（R26）。

规则卡以 `analysis/rule-card.json` 为准（决策 1A）。`rule-card.md` 和 `mandatory-checklist.md` 是脚本生成的视图，给用户看，不手改，也不从视图倒推内容。

## 一、步骤

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --start 2
python -X utf8 "<skill目录>/scripts/scaffold_rule_card.py" <项目目录>                    # 第二节
#   对照原文逐字段核实、填写 rule-card.json                                                # 第三至五节
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --check rule-card      # 问题清零
#   请用户看 rule-card.md 和 mandatory-checklist.md，用户明确同意后：
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --confirm rule-card      # 同时出资料清单，第六节
#   招标文件规定了格式的，按 stage-6-assembly.md 第二节出差异和样张，用户同意后确认
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 2           # 第七节
```

## 二、出候选

`scaffold_rule_card.py` 只读类别为招标文件、提取状态为 `ok` 的文本，工程量清单（.xlsx、.xls）也在内。图纸和响应样本不参与解标。阶段 1 没通过时，它直接拒绝（R9）。

产出：

- `analysis/rule-card.json`：规则卡骨架，带候选。项目里已有规则卡时不覆盖，候选另存为 `analysis/rule-card-候选-<时间>.json`，由你对照后手工并入。
- 规则卡的两个视图：`rule-card.md` 和 `mandatory-checklist.md`。

它做两类事：

- **给出建议值**：项目名称、评标办法、评审轨道和判定信号、AI 条款、暗标条款、评审内容、档次与评分区间、评审注释、篇幅上限、工期、质量标准、安全目标。项目名称按"1.1 项目名称：""2.1 招标项目名称："这类标签取（招标文件优先，补遗答疑其次，清单最后），各处的不同写法都列进候选；一处标签都没有才退回封面标题。
- **只列候选、不填值**：入围规则、初步评审表、强制条款、格式。强制条款候选里包括招标文件点名要施组阐述的内容：前附表 3.7.1"施工组织设计编制的特殊要求"（本项目重点难点、危大工程清单）和第七章"重点难点及危险性较大的分部分项工程"一节，整条摘出。
- **青天启用情况的候选**：有 AI 类人评审条款，或评标办法是技术评分合理价格法，建议写`启用`并带上信号；都没有就留空，由你读原文定。`rule_scope` 按建设地点和资质给候选（第三节 `qingtian`）。
- **四种以外的评标办法**：只认"评标办法采用××法"这类句式，转引句不算。脚本不给轨道建议，见第四节。
- **工程类别的线索**：资质要求、招标范围的原文，工程量清单的工作表名，清单编码对上各张已交付类别知识卡的行数，最后一条写"可能涉及"哪几类、各对上了哪些线索。`value` 留空，主类别不预填（第三节 `project_category`）。
- **答疑、补遗的更正**：找到"原内容……现澄清更正为……""删除招标文件……"这类写法时，逐处摘进可选字段 `addenda_changes.candidates`（第三节 `addenda_changes`）。
- **带原文定位的字段**：勾选框、关键日期、最高投标限价给出建议的行；资格条款、表外致命项、定标规则只列候选，每条带一份现成的 `ref`（第三节《带原文定位的字段》）。
- **项目画像**：定标方式、递交方式、采购体系和方式等八项，找到的给建议的行，没找到的留空（第三节《项目画像和触发项》）。
- **投标文件格式**：逐节列出商务、技术、报价文件的节和小节，并和各自的目录比对。类型和字段名只给候选（第三节《投标文件格式》）。可以单独跑 `python scripts/scan_bid_forms.py <项目目录>` 看大纲，只读。

每个字段的 `candidates` 列出它找到的原文片段，出处写成"文件 第 N 页（提取文本第 M 行）"。

候选只是线索，不是结论。所有字段的 `checked` 都是 `false`，必须逐条回到原文核实。常见的错法有三种：

- 抓到了示范文本里的样例文字；
- 公告和前附表的取值不一致，只抓了其中一处；
- 评审内容在原文里分了多行或带了子项，被切错。

## 三、核实与填写

每个字段都有四个键（带原文定位的 6 个字段、投标文件格式的 2 个字段和项目画像例外，见本节后面）：

| 键 | 写什么 |
|---|---|
| `value` | 取值 |
| `basis` | 依据，只能是以下三种之一 |
| `source` | 出处：文件、章节、页码，补遗写补遗编号 |
| `checked` | 核对原文后改为 `true` |

`basis` 的三种写法：

- `招标文件`：取值来自招标文件或补遗。
- `示范文本默认`：招标文件没写、沿用示范文本的规则，出处写示范文本页码（如篇幅上限沿用"最多不超过 50 页"，出处"示范文本 p61"）。项目名称、青天启用情况、工程类别、评标办法、评审轨道、工期、质量标准、安全目标、强制条款是本项目自己的取值，不能写这一项。规则依据范围不是合肥房建市政的项目，示范文本只作参考，所有字段都不能写这一项。
- `招标文件未规定`：招标文件确实没写。`value` 留空，不要写成"无"。

`candidates` 核实完可以删，留着不影响校验。

填写时守住以下几条：

- **原文照录**：评审内容、档次、注释、初步评审表、强制条款、AI 条款和暗标条款，一字不改，包括标点和序号外的全部文字（R3）。
- **补遗优先**：补遗改过的字段，取补遗的值，出处换成补遗。不得两个值并列。
- **要求还是建议**：篇幅上限的 `kind` 按原文措辞判断。"应""须""不得"写"要求"；"建议""宜""可"写"建议"。判不清就硬停。
- **数值带单位，照原文**：如工期写"240日历天"。投标函上的工期、质量标准必须与这里一致（R22）。

| 字段 | 写法 | 必填 |
|---|---|---|
| `project_name` | 封面上的项目名称原文；与开工登记不一致时硬停 | 是 |
| `qingtian` | 招标文件启没启用青天、规则依据范围，见下文 | 是 |
| `project_category` | 工程类别 `{"main", "modules", "scenarios"}`，见下文 | 是 |
| `evaluation_method` | 招标文件原文的名称。合肥四种是技术评分合理价格法、综合评估法、动态合理价格法、定性定量评审法，其他办法见第四节 | 是 |
| `track` | 见第四节。`signals` 列判定信号，每条含原文 `text` 和 `source`；T-定档 另写 `handoff` | 是 |
| `ai_clause`、`blind_clause` | AI 类人评审条款、暗标条款的整句原文；没有就写"招标文件未规定" | 否 |
| `review_items` | `[{"no": 1, "title": "工程概况"}, ...]`。`no` 从 1 连续编号，`title` 是评审内容原文，顺序与招标文件一致。施组一级标题照此写（R3、R4、Q1） | 是（T-合格 可未规定） |
| `grading` | 档次与评分区间原文，含"未提供的，不得分" | 是（T-合格 可未规定） |
| `review_notes` | 评审表注释原文，含编制建议和"如不符合上述要求将酌情扣分"这类扣分句（照原文留着，脚手架摘要单列扣分句） | 否 |
| `page_limit` | 页数（整数）和 `kind`（要求或建议） | 否；没写时合肥房建市政按示范文本默认，其余写"招标文件未规定" |
| `schedule`、`quality_standard` | 原文取值 | 是 |
| `safety_target` | 原文取值 | 否 |
| `shortlist_rule` | 入围与推荐规则原文 | 是（评标办法不在合肥四种之内的可未规定） |
| `preliminary_review` | 见下文 | 是 |
| `mandatory` | 见下文 | 是 |
| `format` | 见第五节 | 二选一必写 |
| `qualification` | 资格条款，见《带原文定位的字段》 | 是 |
| `checkboxes` | 勾选框原文，同上 | 否 |
| `key_dates` | 关键日期，同上 | 是（投标截止必须找到，其余三个可写未规定） |
| `off_table` | 表外致命项，同上 | 否 |
| `award` | 定标规则原文，同上 | 否 |
| `price_limit` | 最高投标限价，同上 | 否 |
| `bid_forms` | 投标文件格式的节和小节，见《投标文件格式》 | 是（找不到硬停） |
| `bid_forms_diff` | 目录和正文的差异，同上 | 否（有差异就要用户决定） |
| `profile` | 项目画像，见《项目画像和触发项》 | 是（八项每项一行，没写的写未规定） |

`qingtian` 记招标文件有没有启用青天，以及导则和示范文本管不管得到这个项目（决策 D11）：

```json
"qingtian": {"value": "启用", "rule_scope": "合肥房建市政",
             "signals": [{"text": "启用合肥公共资源交易大模型AI“类人”评审功能辅助评标", "source": "第三章 详细评审标准注 2"}],
             "user_decision": "", "basis": "招标文件", "source": "第三章 详细评审标准注 2", "checked": true}
```

- `value`：`启用`、`未启用`或`判不清`。信号见 `hefei-rules.md` 第一节，只写了人工智能初步筛查或初步评审辅助的不算启用。招标文件没提到青天的写`未启用`，`source` 写查过哪几章。`判不清`会硬停，问用户。
- `rule_scope`：`合肥房建市政`、`合肥其他`或`合肥以外`。脚本的候选只看建设地点和资质，你对照原文定。只有合肥房建市政能写`示范文本默认`；另外两种招标文件没写就写`招标文件未规定`，`rule-card.md` 写明导则和示范文本只作参考。
- `signals`：判`启用`时必填，每条含原文 `text` 和 `source`。
- `user_decision`：`未启用`又`合肥以外`时必填，写用户决定停下还是只借用红线和格式能力的原话。先告诉用户规则不保证适用；不代写，用户没说就不往下走。
- 判`未启用`时，轨道不能是 T-AI，`ai_clause` 也不能有值。对不上就回原文核实。

`project_category` 是工程类别，决定阶段 4、5 用哪几张类别知识卡（`references/category-cards/`，决策 5-2A）：

```json
"project_category": {"value": {"main": "土建工程", "modules": ["建筑智能化工程"], "scenarios": ["既有设施改造"]},
                     "basis": "招标文件", "source": "第二章 2.9 招标范围；工程量清单各单位工程", "checked": true}
```

- `main` 是主类别，写占比最大的工程类型（导则 1.3.3（1））。占比看清单各单位工程的金额和招标范围，脚本不算；你按金额提出，第六节请用户确认时说明依据。几类金额相近判不清的，硬停，问用户。
- `modules` 是涉及专业：招标范围里的其他专业，不重复主类别。没有就留空列表。
- `main` 和 `modules` 不限名录（决策 D11）。名录有导则 1.3.2 的 9 类（土建工程、通风与空调工程、装饰装修工程、电梯工程、道路工程、给水工程、排水工程、园林工程、绿化工程）和 3 个专业（建筑电气与照明工程、建筑给排水与消防工程、建筑智能化工程），用名录的名称才用得上知识卡。名录没有的照招标文件的叫法写，`rule-card.md` 写明没有知识卡，阶段 4、5 不预填控制点、不查 W9，只按招标文件和红线写，不编规则。
- `scenarios` 是场景：在既有建筑或设施上施工的（利旧改造、加固、修缮、拆除、不停用施工）选既有设施改造，否则留空列表。
- 第二节的候选只是线索：清单编码对上的行数不是造价占比，招标范围里的字也可能是别的意思，逐条对照原文。
- 13 张卡已全部交付。卡片目录里缺了选到的卡（安装不全）时，`rule-card.md` 写明"尚未交付"，阶段 4、5 先跳过它们，不影响确认。

`preliminary_review` 照录初步评审表全表（形式、资格、响应性），每行写成：

```json
{"id": "PR03", "stage": "2.1.3 响应性评审", "factor": "工期", "standard": "<评审标准原文>",
 "file": "商务", "tech_related": true, "requirement": "施组工期与招标文件、投标函一致"}
```

- 与施组有关的行，`tech_related` 写 `true`，并在 `requirement` 写明对施组的要求。投标文件格式、工期、质量标准三行一定与施组有关（Q0），逐行核对不要漏标。脚本只能查出"一行都没标"，查不出漏标了哪一行：评审因素是原文，各招标文件写法不一，脚本不按文字匹配。
- 资格、签字盖章等与施组无关的行，`tech_related` 写 `false`，照样列出，阶段 8 提交前清单要用。
- `id` 从 PR01 起，不重复。
- `file` 写这一行由哪个文件满足：`商务`、`技术`或`报价`。写`技术`的行 `tech_related` 必须是 `true`；工期这类同时落在投标函和施组的行，`file` 写投标函所在的文件，`tech_related` 仍写 `true`。

`mandatory` 列全部★条款、实质性要求、否决条款和招标指定的施组内容，每条写成：

```json
{"id": "M01", "type": "★", "text": "<条款原文>", "source": "第二章 3.7.5"}
{"id": "M05", "type": "★", "text": "<条款原文>", "source": "第二章 3.4.1", "scope": "提交前清单"}
{"id": "M06", "type": "招标指定", "text": "<重点难点条款原文>", "source": "第二章 3.7.1", "keywords": ["成品保护", "专项改造方案"]}
```

- `type` 只能是 `★`、`实质性`、`否决`、`招标指定`。
- 工期、质量标准各列一条"实质性"；招标文件写了安全目标的，安全目标也列一条（R5、R22）。
- **招标指定**：招标文件点名要施组阐述的内容，典型是前附表 3.7.1 的"本招标项目重点难点"和"危险性较大的分部分项工程清单"，注明"本项内容与施工组织设计重难点评审相对应，投标人必须在施工组织设计中全面重点阐述"。要求：
  - 重点难点和危大清单分开登记，各一条，`text` 照录原文；"投标人投标时应补充完善危险性较大工程清单并明确相应的安全管理措施"这类要求和它们写在同一条里。
  - `keywords` 必填：从条款原文里摘正文必须写到的叫法，每条重点难点至少一个（如"成品保护""专项改造方案""脚手架工程"）。只能摘原文的字，不换说法（R15），脚本会核对。门禁 B9 逐个查落点那一项的正文有没有写到，不能放行。
  - 去处只能是施组。危大清单写"/"的，照录"/"；重点难点只剩"补充完善危大清单"一句的，仍按招标指定登记。
- `keywords` 也可以加在别的类型上，B9 同样逐个核对；没有可比对数值的条款（如按第八章格式提交）加了关键词，就不再留给阶段 7 人工核对。
- 编号从 M01 起，不重复。
- `scope` 写这条在哪里落实（决策 4c-4A），只能是：
  - `施组`：不写即是。阶段 4 响应矩阵按编号给每条找落点，门禁 B9 核对。工期、质量标准、安全目标，以及按第八章格式提交施组这类条款，都是施组。
  - `提交前清单`：施组里落实不了的商务、递交类条款，如投标保证金、投标有效期、项目经理承诺、"不得递交备选方案"、电子签章与加密。不在施组里找落点，阶段 8 提交前清单逐条勾选，只能勾、不能记不适用。
  - `商务文件`、`报价文件`：落实在这两个文件里的条款，如投标函内容、报价文件的编制要求。商务线做完前，这两种都并入阶段 8 提交前清单，逐条勾选，清单上写明对照哪个文件。这是临时做法，第 5 步合龙时改成在商务线、报价线落点。
  - 拿不准的按施组登记，阶段 4 找不到落点时再和用户核对。没有一条去施组的，脚本拒绝。
  - 评标办法前附表里"……的，不得被推荐为中标候选人"这类条款（如投标报价低于成本、拒不澄清），不在施组里落实，登记为提交前清单。
- 含义不清的条款硬停，问用户，不按字面猜（R27）。

`addenda_changes` 是可选字段，脚本在答疑、补遗里找到更正时才出现：

```json
"addenda_changes": {"candidates": [{"text": "<原内容……现澄清更正为……>", "source": "答疑.pdf 第1页（提取文本第31行）"}], "checked": false}
```

- 逐条对照原文，把更正落到相应字段，以更正后的为准，出处换成答疑编号（补遗优先）。
- 只改了一部分的，没改的照旧。例：答疑把危大清单改成"/"，但"补充完善危大清单并明确安全管理措施"的要求还在，这条招标指定照样登记。
- 与施组无关的更正（如项目经理业绩、履约保证金）：是★、实质性或否决条款的，按更正后的原文登记为提交前清单；别的列给用户，提醒商务文件按更正后的写。
- 全部核对完把 `checked` 改为 `true`，否则校验不过、不能请用户确认。

### 带原文定位的字段（决策 3A）

下面 6 个字段的出处逐行写 `ref`，不写 `source`。字段本身只有 `value`、`basis`、`checked`，依据只能是`招标文件`或`招标文件未规定`。两种写法并存是临时的，v2.1 把老字段也迁到 `ref`。

`ref` 写成 `{"file": "招标文件.pdf", "page": 11, "line": 384, "keyword": "有，最高投标限价"}`：

- `file`：提取报告里招标文件的文件名，补遗写补遗的文件名。图纸和响应样本不算。
- `line`：提取文本的行号，从 1 起。`page` 是这一行所在的页，没有分页的文本（docx、xlsx）留空。
- `keyword`：这一行起 3 行内的原文，至少 2 个字，空白不计。
- 校验按行号回到提取文本查关键词，查不到就不过。补遗后文本变了，同样查不到。候选里的 `ref` 都查得回来，核实后可以直接抄。

`qualification` 是资格条款，一个评审因素一行：

```json
{"id": "QU01", "factor": "项目经理资格", "text": "<条款原文>",
 "pointer_chain": ["第三章 2.1.2 资格评审标准", "第二章前附表 1.4.1", "附录 5"],
 "requirements": ["二级及以上注册建造师", "安全生产考核合格证书（B 证）"], "ref": {"...": "..."}}
```

- 合肥的资格条款常是一串指针："见评标办法前附表"，再"符合第二章第 1.4.1 项"，再"见附录 5"。`pointer_chain` 写顺着找到原文的路径，`ref` 指原文所在的行；原文就在这里的写空列表。
- `requirements` 把条款拆成逐项要求，不能为空。脚本只列候选，由你读原文拆。

`checkboxes` 是勾选框原文，分包、联合体、保证金、备选方案都从这里读：

```json
{"id": "CB04", "label": "1.11.1 分包",
 "options": [{"text": "不允许", "checked": false}, {"text": "允许，分包内容：<原文>", "checked": true}],
 "count": 1, "ref": {"...": "..."}}
```

- 脚本按 ☑、□ 读，一组一行。条款名称可能折行、串进页眉或读不到，选项只取到行尾，都要对照原文改。
- 有的选项提取时丢了勾选框，字跑进 `label`（如"是否要求投标人提交投标保证金：不要求"），要补回 `options`。
- 投标文件格式一章里留给投标人填的勾选框（如"目前未在其他项目上任职"）不是招标人的选择，脚本不读。
- `count` 写勾了几个。不是 1 个的要写 `note`：多选的照录；一个都没勾的是招标文件的疑点，列给用户，不猜。

`key_dates` 是关键日期，四个事项每个一行：

```json
{"id": "KD01", "kind": "投标截止", "text": "<原文>", "deadline": "2026-12-10 10:00", "ref": {"...": "..."}}
{"id": "KD02", "kind": "澄清截止", "text": "<原文>", "deadline": "2026-11-20 17:00", "ref": {"...": "..."}}
{"id": "KD03", "kind": "异议截止", "text": "<原文>", "deadline": "2026-11-30 10:00", "ref": {"...": "..."}}
{"id": "KD04", "kind": "询标时限", "basis": "招标文件未规定"}
```

- `投标截止` 必须找到，`deadline` 必填。其余三个招标文件确实没写的，这一行写 `"basis": "招标文件未规定"`，不写 `text`、`ref`。
- `deadline` 写成 `YYYY-MM-DD HH:MM` 或 `YYYY-MM-DD`。只写了"投标截止时间 10 日前"的，脚本按投标截止倒推，你核对一下。询标时限是时长，`deadline` 留空。
- 补遗顺延投标截止的，取补遗的值，`ref` 指补遗。

`off_table` 是表外致命项：评审表之外、会导致废标或不被推荐的条款，如注册建造师人数、入围复核、询标时限、递交解密、智慧信息库引用。一条一行，写成 `{"id": "OT01", "kind": "注册建造师人数", "text": "<条款原文>", "ref": {...}}`。脚本只列候选。

`award` 是定标规则原文，如是否授权评标委员会确定中标人。一条一行，写成 `{"id": "AW01", "text": "<条款原文>", "ref": {...}}`。入围和推荐规则写在 `shortlist_rule`，这里不重复。

`price_limit` 是最高投标限价，这个字段的 `value` 是一个对象，不是列表：

```json
"price_limit": {"value": {"is_set": true, "value": "<数字或公布方式，照原文>", "ref": {"...": "..."}},
                "basis": "招标文件", "checked": true}
```

- 这是招标人公布的数字，可以进规则卡；门禁 B13 只拦施组里的金额。
- 脚本按勾选框判，只取一行内的字，折到下一行的要补全。勾了"无"的，`is_set` 写 `false`，`value` 留空，`ref` 指这一行。

### 投标文件格式（`bid_forms`、`bid_forms_diff`）

这一章决定商务文件、报价文件要填什么。脚本按标题找（`第×章投标文件格式`、`响应文件格式`），不认第几章；按封面的（商务文件）（技术文件）（报价文件）分文件，读出每个文件的目录和正文的节、小节，生成一节一行的草稿。这两个字段和上面 6 个一样不写 `source`，出处写在行里。

```json
{"id": "S03", "title": "法定代表人身份证明或授权委托书", "number": "二", "toc_number": "二", "in_toc": true, "file": "商务",
 "ref": {"...": "..."},
 "parts": [{"id": "S03-1", "title": "法定代表人身份证明", "kind": "字段值", "fields": ["单位性质", "地址"],
            "attachments": ["法定代表人身份证正反面扫描件"], "protected": [], "not_required_basis": null,
            "ref": {"...": "..."}, "hints": {"...": "..."}}]}
```

- 每节至少一个小节，没有小节的列一个同名小节。封面也算一行，`in_toc` 是 `null`。
- `file` 写`商务`、`技术`或`报价`。脚本读不到封面时留空，你按原文补上。
- `kind` 必须由你对照原文写：`字段值`、`正文`、`附件`或`无需提供`。脚本只在 `hints` 里给候选，`hints` 不算数，也永远不提示`无需提供`。
- `字段值`类型要列 `fields`。`hints.fields` 是从"姓名：性别："和表格格子读的，提取文本丢了不少表格线，对照原文补全再抄。
- `无需提供`要在 `not_required_basis` 写招标文件的依据（如勾选框 `CB04`）。招标文件没有依据的，写用户原话，不代写。
- `attachments` 写这一节要附的材料，`protected` 写不得改动处（如"第 1 条不填金额"）。两个都是文字列表，没有的留空。
- `hints.conditional` 为真的，标题带"如有""如要求"，要不要提供看招标文件这一项的规定。

脚本读不出来的（这一章叫别的名字、格式特殊），照原文逐节手填，`ref` 照样要查得回来。

`bid_forms_diff` 是目录和正文的差异，一条一行：

```json
{"id": "SD01", "file": "商务", "title": "商务文件详细评审资料", "in_toc": false, "in_body": true,
 "toc_number": null, "body_number": "八", "default": "<脚本写的默认做法>", "decision": "<用户的决定>"}
```

- 差异有三种：正文多一节、目录多一节、节名相同编号不同。真实招标文件三种都见过。
- `decision` 只写用户说的话，不代写。把差异和 `default` 告诉用户，澄清窗口开着的同时提醒可以在线提出。
- 校验会重扫一遍，从表里删掉一节或一条差异都过不了。
- 没有差异时脚本把依据写成`招标文件未规定`，`value` 留空，不用改。

### 项目画像和触发项（`profile`）

`profile` 记招标文件自己的几项情况，地区不在这里，写在 `qingtian.rule_scope`。八项，每项一行：

```json
{"id": "PF01", "kind": "定标方式", "text": "7.1 是否授权评标委员会确定中标人：是", "ref": {"...": "..."}}
{"id": "PF05", "kind": "专门面向中小企业", "basis": "招标文件未规定"}
```

| 事项 | 写什么 | 脚本怎么找 |
|---|---|---|
| `定标方式` | 是否授权评标委员会确定中标人 | 先读前附表的勾选框 |
| `递交方式` | 电子递交、是否还要非加密文件 | "递交电子投标" |
| `采购体系` | 写了政府采购的照录；招标投标体系没有专门写法的，写未规定 | "政府采购" |
| `采购方式` | 公开招标、邀请招标、竞争性磋商等 | 按磋商、谈判、邀请、招标公告的顺序找 |
| `专门面向中小企业`、`节能产品` | 招标文件确有这类要求才写；只是一般政策说明的写未规定 | 同名的字 |
| `证书查询验证` | 证书要投标人自行查询验证的条款 | "查询验证"、扫描二维码 |
| `现场限制` | 不停工、多现场、局部施工这类限制 | 几个常见说法 |

- 脚本找到的给一行建议，摘录要改成原文那一句。没找到的 `text`、`ref` 留空，你读原文补上；招标文件确实没写的，这一行的 `basis` 写`招标文件未规定`。脚本没找到不等于招标文件没写。
- `rule-card.md` 第八节按卡算出这个项目命中哪些触发项，只列命中和判不清的，做法在对应步骤落地。

命中下面四项的是硬停：本 Skill 的规则按招标投标体系写，这几项没有覆盖。告诉用户，用户决定怎么继续，把用户原话写进这一行的 `user_decision`，不代写，也不劝说。

- `采购体系`的原文里有"政府采购"；
- `采购方式`的原文里有"磋商"；
- `专门面向中小企业`、`节能产品`写了原文。

## 四、判定评审轨道

依据 `hefei-rules.md` 第二节。

先按原文判招标文件有没有启用青天，不凭项目名称或地区猜：信号见 `hefei-rules.md` 第一节《青天的使用范围》，不同情况怎么办见 SKILL.md《适用范围》。

| 评标办法 | 可判的轨道 | 必须有的信号 |
|---|---|---|
| 技术评分合理价格法 | T-AI | 评标办法原文 |
| 综合评估法 | T-AI 或 T-暗标 | 判 T-AI 须有 AI 条款原文，判 T-暗标 须有暗标条款原文 |
| 动态合理价格法 | T-合格 | 评标办法原文 |
| 定性定量评审法 | T-定档 | 评标办法原文；`handoff` 写明定标部分由用户另行编制（R24） |

- 定性定量评审法的招标文件即使启用了 AI 类人评审，也判 T-定档，写作目标按定档。AI 条款照录进 `ai_clause`，阶段 4、5 按 AI 评审逻辑一并写。
- AI 条款与暗标条款同时出现，脚本不给建议，校验报硬停。请用户向招标人澄清，不自己选。
- 评审内容与示范文本结构不同且含义不清，硬停。
- 评标办法不在上表四种之内的不硬停（决策 2A）：`evaluation_method` 照录原文，脚本不给轨道建议，你按 AI、暗标条款等信号提出轨道，请用户确认，确认时说明没有导则依据（`rule-card.md` 第一节会写明）。判 T-AI 须有 AI 条款原文，判 T-暗标 须有暗标条款原文。入围规则招标文件没写的，写"招标文件未规定"。
- T-合格 的技术文件不打分，评审内容、档次可以写"招标文件未规定"。即便如此，初步评审表和强制条款照样必填。

## 五、格式

`format` 只记指针，不在规则卡里重复格式规定。二选一：

1. **招标文件规定了格式记录里的字段**（字体、字号、行距、页边距、目录、页码、暗标等，含评审注释里的编制建议）：
   - 按 `stage-6-assembly.md` 第二节写 `analysis/tender-format.json`；评审注释有扣分句的，照抄进它的 `penalty`；
   - `format.value.tender_format` 写 `"analysis/tender-format.json"`，`basis` 写"招标文件"，`source` 写规定所在的章节和页码。
2. **都没规定**：`no_rules` 写 `true`，`basis` 写"招标文件未规定"，沿用开工所选。

两种情况下，格式记录装不下的规定（字体颜色、装订、份数、"采用文字并结合图表形式编制"等）都原文照录进 `other_rules`，每条后面括注出处。篇幅上限写在 `page_limit`，不写在这里。

- 评审轨道判不清：四种以外的评标办法按信号提不出轨道；或 AI 条款与暗标条款同时出现。

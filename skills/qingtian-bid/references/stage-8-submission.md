# 阶段 8 提交前清单细则

阶段 7 完成后读。阶段 8 不再改施组，只把投标文件交出去之前要核对的事逐条过一遍：施组成品就是过了门禁的那一份、只交一份；制作、签章、加密与递交；形式评审独立性；报价与投标函；商务侧红线；初步评审表里与施组无关的行；去处为提交前清单的强制条款。清单由脚本现算，和用户逐条核对，用户认可一条勾一条。

本 Skill 不上传、不签章、不加密，这些由用户在电子交易系统的投标文件制作工具里完成。商务文件由用户另行编制，本版本暂不生成；报价由公司决定。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。命令在哪个目录运行都可以。所有材料只在本机处理，不外传（R26）。

## 一、前提：阶段 7 完成

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 7
```

阶段 7 的完成条件见 `stage-7-gates.md` 第八节。阶段 7 没完成时，勾选一律拒绝，概览显示"提交前清单：—（阶段 7 完成后核对）"。

## 二、步骤

```powershell
#   1. 出清单视图 review/submission-checklist.md，看有哪些条目
python -X utf8 "<skill目录>/scripts/submission_checklist.py" <项目目录>
#   2. 和用户逐条核对（第四、五节）；用户明确认可一条，勾一条
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --tick <编号>
#   3. "可记不适用"为是的条目，用户说明不适用的理由后
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --not-applicable <编号> --reason "<用户说明的理由>"
#   4. 全部处理完
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 8
```

`submission_checklist.py` 每次重写视图，还有未处理的条目或自动核对问题时退出码为 1。每勾一条、每记一条不适用，视图跟着重写。第一次勾选后阶段 8 记为进行中。

## 三、清单从哪里来

清单每次按三样东西现算，不存可手改的清单（决策 4c-1A）：

- 模板 `templates/submission-checklist.json` 的固定条目，按评审轨道筛选；
- 规则卡初步评审表里 `tech_related` 为 false 的行；
- 规则卡 `mandatory` 里去处 `scope` 为"提交前清单"的条款（决策 4c-4A，写法见 `stage-2-analysis.md` 第三节）。去处为"商务文件""报价文件"的现在也并入这里，清单上写明对照哪个文件；这是临时做法，第 5 步合龙时替换。

`review/submission-checklist.md` 只是视图，手改不起作用，下次运行就被覆盖。勾选记录存在 `project-state.json` 的 `submission.items`。

## 四、核对前先对照招标文件

模板按示范文本编写，具体项目以招标文件为准。核对前和用户一起看招标文件的投标人须知前附表、投标人须知 3.6～3.7（投标文件编制与制作）、4.1～4.2（密封与递交），以及第三章初步评审标准。

- **条目写法与招标文件不同**：按招标文件原文核对。例如前附表写明了非加密投标文件的递交方式，E04 按前附表核对。
- **C01～C07 的合肥形态**：提醒这几条时，把 `redlines.md` 第四节表里的"合肥形态"和"触发"一起告诉用户。清单文字沿用红线原文，合肥招标文件的做法可能不同，例如 C03 的查询结果从"其他材料"窗口上传，信誉不做证明材料。
- **按需触发的条目确实不适用**：E04（前附表不允许或不要求递交非加密投标文件）、C01（招标文件第八章和前附表都没有要求导航表）、C02（招标文件不按五件套、三件套要求证明材料；证明材料的类别改按招标文件和本清单 R 组核对）、C05（招标文件不要求偏离表）、C06（不属于政府采购项目），用户说明理由后记不适用。
- **红线条目与招标文件明显冲突**：不勾，也不能记不适用（决策 4c-3A）。停下来和用户核对招标文件原文；确属模板不适合本项目的，阶段 8 不能完成，按 `templates/DIRECTORY.md` 的维护规则改模板后再核对。
- **招标文件有模板和规则卡都没覆盖的递交类★、否决条款**：这类条款应在阶段 2 登记，`scope` 写"提交前清单"，它们自动进入"去处为提交前清单的强制条款"一组。阶段 8 才发现漏登的，停下来告诉用户补登的代价：要改规则卡，规则卡的确认和依赖改动那几行的确认（事实卡、资源卡、响应矩阵、施组各项）随之失效，没写 `cites` 的行算依赖全部规则行，须按脚本提示逐个重新核对确认，重跑阶段 7 门禁、完成阶段 7，再回到阶段 8。已勾的条目只有文字变了的那几条失效（决策 4c-2A）。补不补由用户决定；不补的，不得在清单外口头记成"已核对"。

## 五、勾选与不适用的规则

逐条对给用户：条目原文、出处，以及要用户确认的具体事实（例如 E03：加密用的是哪一把数字证书，全部内容是否都用它加密，证书到什么时候有效；E06：评标期间由谁守在电子交易系统上回复询标函）。

- **只有用户明确认可这一条，才运行 `--tick`**。用户没回、只说"差不多""都弄好了"，都不算认可。不得替用户勾选，不得一次替用户勾完全部条目。
- **勾选锁定条目的内容**：编号、文字、出处、能否记不适用、是否锁成品（决策 4c-2A）。规则卡改了，只有文字跟着变的条目（P02、P03、R 组、M 组中改动的那一条）在视图里标 ⚠ 失效，重新核对后再勾一次。
- **S01、S02 还锁定成品的 sha256**。勾这两条前脚本先自动核对（第六节），不成立就拒绝。成品再保存过，这两条失效，阶段 7 的条件也随之不成立，回到阶段 7。
- **不适用只给按需触发的条目**：视图"可记不适用"一列为"是"的才行，目前是 E04、C01、C02、C05、C06。理由写用户说明的原话，不得替用户编理由，也不得劝用户记不适用。其余条目都是红线，脚本拒绝记不适用，只能核对后勾选（决策 4c-3A）。
- 重新运行 `--tick` 或 `--not-applicable`，新记录覆盖旧记录。失效的条目、记错的不适用，都这样重新记。

## 六、自动核对

以下由脚本自己核对，不靠用户回答：

- **门禁报告**是当前成品的，而且记的是放行后的结果（与阶段 7 相同）。
- **output/ 下只有一份施组**：除 `output/施工组织设计.docx` 外，`output/` 及其子目录里不能再有 .docx、.doc、.docm、.dotx、.wps 文件。两份以上施组视为备选方案，否决（示范文本 3.6.3）。Word、WPS 打开文件时生成的 `~$` 临时文件不算。多出来的旧稿、副本移出 `output/`。脚本运行时显示多出来的文件名，视图只写个数，不写文件名。

自动核对不成立时，S01、S02 不能勾，阶段 8 不能完成。

## 七、完成阶段 8

```powershell
python -X utf8 "<skill目录>/scripts/project_status.py" <项目目录> --complete 8
```

以下全部满足才能完成，否则脚本逐条列出：

- 阶段 7 的完成条件仍然成立，如成品没再保存过、规则卡没改过、门禁报告是当前成品放行后的结果；不成立的，脚本以"阶段 7 的条件不再成立"开头列出；
- `output/` 下只有一份施组；
- 新建项目的完整 PDF 已导出并记录逐页检查，PDF 与 DOCX 的哈希匹配当前交付记录；
- 清单里每一条都已勾选，或按规则记了不适用，且都没有失效。

完成后交付已验收的 `output/施工组织设计.pdf` 与同版可编辑的 `output/施工组织设计.docx`。按招标文件指定的格式，从这两个同版文件中选其一导入制作工具，与商务文件一起完成规定的签章、加密和递交。两种载体对应同一施组，不并列递交。交付前运行 `export_response_pdf.py <项目目录> --check`，改过的文件须重新出稿并验收。

## 八、本阶段的硬停止

- 用户要你代为勾选、一次勾完全部，或只说"都弄好了"：逐条核对，逐条等用户认可，不替用户勾。
- 用户要把红线条目记不适用：说明决策 4c-3A，不照做；与招标文件确有冲突的，按第四节停下来核对原文。
- 用户要你给报价建议，或为了入围调整报价：不给。报价由公司决定（P03；`hefei-rules.md` 第六节）。
- 用户要在上传前再改施组：回到阶段 5 改中间稿、重新确认，阶段 6 重新出稿，阶段 7 重跑门禁，阶段 8 的 S01、S02 重新勾选。不在成品上直接改内容。
- 用户要另备一份施组，或在施组里并列"方案一、方案二"：说明 S02 和 Q14，两份以上视为备选方案，否决，不照做。
- 用户要借用其他投标人的电脑、网络、造价软件加密锁，或拿别家的投标文件改作底稿：说明 I01～I04 和 Q9，形式评审不通过，不照做。
- 发现漏登的递交类★或否决条款：按第四节停下来，说明补登的代价，由用户决定。
- 用户要在成品里加隐藏文字、写给评审系统看的提示语，或为躲检测故意改写：说明 Q13、Q10，不照做。

# 模拟自评

使用阶段：阶段 7 完成以后，可选。阶段 8 之前、之后做都可以。

**模拟，不是青天的评分。** 模拟自评按招标文件的评分标准，把青天的四个功能走一遍，给每项评审内容一个模拟档次和模拟分，脚本加出总分。它只用来找失分点、决定改哪里，不是门禁，不挡确认，不挡任何阶段。用户说不做就不做。本 Skill 不承诺分数，模拟分也不是预期得分。

命令里的 `<skill目录>` 是本 Skill 所在的目录（SKILL.md 所在目录）。路径可能带空格，引号要留。所有材料只在本机处理，不外传（R26）。

## 一、和预演有什么不同

青天辅助评审有四个功能：评审项解析、溯源解析、类人评审逻辑论述、评审建议（导则 1.3.1，`hefei-rules.md` 第三节）。

| | 类人评审预演（`rehearsal.md`） | 模拟自评（本文件） |
|---|---|---|
| 什么时候 | 阶段 5 每项确认前；阶段 7 对成品 | 阶段 7 完成后，对当前成品 |
| 走几步 | 前三步，只记走不通的地方 | 四步，最后一步给档次和分数 |
| 出不出分 | 不出分数和档次 | 出模拟档次、模拟分和总分 |
| 谁来做 | 最好新会话或子代理，也可以同一会话 | 只能新会话或子代理 |

预演仍然不出分数。想要分数的，做模拟自评，不要让预演打分。

这一版只评本 Skill 出的、过了阶段 7 的成品。评别家的或历史的标书，以及拿公布的真实得分来校准，以后再做。

## 二、四步

| 步骤 | 对应青天哪一步 | 谁来做 | 产出 |
|---|---|---|---|
| 1. 核实评分标准 | 评审项解析 | 写稿的会话 | `review/自评/评分标准.json` |
| 2. 摘出处 | 溯源解析（Q2） | 独立评审人 | 评分表的 `evidence` |
| 3. 写理由 | 类人评审逻辑论述（Q3、Q4） | 独立评审人 | `reason`，该写时加 `full_reason` |
| 4. 给档次和分数 | 评审建议 | 独立评审人给分，脚本核对、加总分 | `自评记录.json`、`自评报告.md` |

## 三、第一步：核实评分标准

```powershell
python -X utf8 "<skill目录>/scripts/self_score.py" <项目目录> --init-standard     # 出候选，不覆盖已有的
python -X utf8 "<skill目录>/scripts/self_score.py" <项目目录> --check-standard    # 核实后校验
```

候选按规则卡的档次原文和招标文件出：示范文本的结构，一个评审因素"施工组织设计"整体打分，各项评审内容都归它（`hefei-rules.md` 第四节）。候选只是线索，逐个字段对照招标文件原文核实：

| 字段 | 写什么 |
|---|---|
| `id` | 按顺序写 U1、U2…… |
| `name` | 评审因素原文，如"施工组织设计" |
| `points` | 分值，招标文件写多少就是多少 |
| `items` | 这个评审因素打分的评审内容编号（规则卡的编号）。每项评审内容只归一个评审因素，一项不漏 |
| `method` | `区间`或`固定分值` |
| `bands` | 区间法的各档：`name`、`low`、`high`、`low_closed`、`high_closed`。示范文本是一般 0＜F≤60、良好 60＜F＜90、优秀 90≤F≤100 |
| `values` | 固定分值法可取的分值，从小到大，最大的等于分值。导则 2.2.2 方法 2 是分值的 60%、70%、80%、90%、100% |
| `criteria_text` | 评分标准原文，从评审因素那句照抄到档次那句 |
| `points_ref`、`criteria_ref` | 分值和档次在提取文本里的位置，写法同规则卡的 `ref`（`stage-2-analysis.md` 第三节"带原文定位的字段"），校验时回原文查 |
| `checked` | 核实后改为 `true` |

几种常见的写法：

- **整体打分**（示范文本）：一个评审因素，`items` 是全部评审内容，评审人每项给一个分，再给一个整体分。
- **逐项给分值**：每项一个评审因素，`items` 只有一个编号，各项分值照原文写。总分是各项相加。
- **区间法**的档次要从 0 分连到分值，相邻两档的边界只归一边（导则 1.3.3（2）：打分区间连续不间断）。抄出来断开或重叠的，先核对抄录。原文确实如此，告诉用户。
- 招标文件的打分写法看不懂，或和这两种结构都对不上：停下来问用户，不猜。
- 技术文件不打分的项目（T-合格），没有可模拟的评分标准，不做自评。

评分标准不进卡片的确认流程。核实时把分值、档次和覆盖哪几项给用户看一眼。

## 四、第二～四步：独立评审人评分

```powershell
python -X utf8 "<skill目录>/scripts/self_score.py" <项目目录> --packet                  # 出评审材料和空评分表
python -X utf8 "<skill目录>/scripts/self_score.py" <项目目录> --record <评分表.json>     # 核对、存记录、出报告
python -X utf8 "<skill目录>/scripts/self_score.py" <项目目录>                           # 看状态
```

`--packet` 只在阶段 7 已完成、门禁报告就是当前成品时才出。它写两个文件到 `review/自评/`：

- `评审材料.md`：评分标准原文，加成品按一级标题分节的全文；
- `评分-待填.json`：空评分表，带当前成品的 sha256。

**谁来评**：只能是新会话或子代理，记录写 `新会话` 或 `子代理`。写稿的会话看过响应矩阵和中间稿，知道自己想写什么，会把成品没写出来的内容脑补进去，给分偏高。脚本不收 `同一会话`。

**只给他看**：`评审材料.md`、事实卡视图 `analysis/project-facts.md`、`评分-待填.json`。**不给他看**：响应矩阵、中间稿、资源卡、门禁报告、写稿时的对话。评委和青天手里只有招标文件和投标文件。

给子代理或新会话的提示可以这样写：

> 你在模拟评委按招标文件的评分标准给一份施工组织设计打分。只读 `评审材料.md`、`project-facts.md` 和 `评分-待填.json`，不读别的文件。逐项评审内容做四件事：一，到这一项的章节里找响应，逐字摘一到三句能直接引用的原文写进 evidence；二，按评审内容和档次原文写给分理由 reason，说清本项目事实、具体做法、量化指标、依据规范编号这四样有没有；三，给档次 band 和分数 score，分数要落在所给档次里；评到分值的 60% 及以下或 90% 及以上（固定分值是满分或 0 分），在 full_reason 里写出充足理由；四，没给满分的，lost 写扣在哪，fix 写怎么改。成品里没有这一项内容或明显不符的，provided 写 false，0 分，full_reason 写清楚。整体打分的评审因素，在 units 里再给一个整体分和理由。不改稿，不编材料里没有的内容，不预测能否入围、中标。reviewer 写"子代理"（新会话就写"新会话"）。填好的表另存一个文件，把路径告诉我。

脚本核对这些，有一条不符就不存：

- 每项评审内容都评了，按顺序一项一条；
- 区间法的档次存在、分数落在这一档里；固定分值法的分数是可取的分值之一，`band` 留空；
- 分数在 0 到分值之间，最多两位小数；0 分只给未提供的（`provided` 为 `false`）；
- 该写充足理由的写了：区间法是分值的 60% 及以下和 90% 及以上（导则 2.2.2 方法 1），固定分值法是满分和 0 分（方法 2）；未提供的都要写；
- 出处逐字摘自本项的章节，每条 6～200 字。写在别的项里的内容不算本项的，要记进失分点（Q2）；
- 没给满分就写失分点，写了失分点就写怎么改；
- 整体打分的评审因素，整体分在各项分的最低和最高之间；
- 不写"稳了""能进前 5""能中标""保证得分"这类说法；
- 评分表只能有规定的字段。评审人自己写的总分会被拒，总分由脚本算。

存下的记录锁定成品和评分标准的 sha256。报告写在 `review/自评/自评报告.md`：总表、评分标准原文、逐项表（评审内容、分值、评分标准原文、模拟档次、模拟得分、理由和成稿出处、失分点、怎么改）和怎么用。

## 五、结果怎么用

- 报告原文告诉用户，开头那句"模拟，不是青天的评分"一起说。用户问能拿多少分、能不能入围，回答模拟分是多少、它从哪来、不能当预期得分。不预测入围和中标。
- 改不改、改哪几项由用户定。要改的，回阶段 5：`project_status.py <项目目录> --reopen 5`，改中间稿、逐项重新确认，再出稿（阶段 6）、过门禁（阶段 7），然后重做 `--packet` 和评分。
- 补的是本项目的事实、做法、指标和依据。卡片里没有的回阶段 3 补卡，不编（R7）。
- 不为了分数堆关键词、重复评审内容原文（Q6），不加写给评审系统看的文字（Q13）。
- 前后两次自评的分数可以互相比，看改稿有没有用。最好用同一类评审人。不跟别的项目、别家的标书比。

## 六、什么时候作废

下面任何一种情况，记录显示"要重评"，进度摘要里那一行也会写出来：

- 成品再保存过（sha256 变了）；
- 评分标准改过；
- 阶段 7 重开了（如补遗后重新解标、改稿）。

作废后要重评的，先过阶段 7，再从 `--packet` 做起。记录写坏了读不出，按没做算。

## 七、不能做的

- 不把模拟分说成预期得分，不说"稳了""能进前 5""能中标"。本 Skill 不承诺分数。
- 不用官方评审系统试探打分（Q13；暂行办法第六条、第二十二条）。
- 不把成品或评审材料贴到网页版或其他在线工具（R26）。
- 不评外来的标书，不评没过阶段 7 的稿子。
- 不由写稿的会话自己评。
- 自评不是用户确认，不替用户勾选提交前清单。

## 八、局限

- 青天和评委怎么打分没有公开。各评审内容之间有没有内部权重、良好档内的分数怎样细分，都没查到（`hefei-rules.md` 第十三节）。整体打分时，整体分怎样由各项合成，是评审人的判断【推断】。
- 没有真实得分校准，模拟分可能整体偏高或偏低。
- 脚本只核对格式、边界和出处是不是原文，看不出评得准不准。
- 新会话或子代理只是换了一个读者，不是青天，也不是评委。

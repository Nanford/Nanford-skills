# 采购体系与采购方式路由（P3-1）

> 使用阶段：开工必问 → 阶段0登记 → 阶段2精修 → 阶段4/5/6 全程约束。
> 落盘：`analysis/project-profile.md` 第一/第二节 + `project-state.json` 的 `procurement_system` / `procurement_mode`。
> 磋商/谈判/询价类另落盘 `analysis/consultation-strategy.md`（模板 **`templates/磋商响应策略表.md`**）。
> `gov` 体系另落盘 `analysis/gov-policy-checklist.md`（模板 `templates/政府采购政策核对表.md`）。
> **先定"谁在采购、按什么方式采购"，再定项目类型，最后才套写作骨架。**
> 顺序错了就会出现"给竞争性磋商项目交《投标函》"这类硬伤。

## 一、采购体系（两选一，决定法律框架与专属得分项）

| 代码 | 名称 | 识别信号 | 法律框架 | 专属动作 |
|---|---|---|---|---|
| `gov` | **政府采购** | 采购人为行政机关/事业单位/团体组织；出现"政府采购法""财库〔20XX〕XX号""中国政府采购网""政采云/省级政府采购平台"；资格条款引用《政府采购法》第二十二条 | 政府采购法 + 实施条例（工程类另适用招标投标法） | **必读 `gov-procurement-policy.md`**，填 `gov-policy-checklist.md` |
| `enterprise` | 企业/国企自主采购 | 采购人为烟草工业公司、物流公司、集团企业；引用《招标投标法》或企业自有采购管理办法；平台为公e采/中招联合/中化商务等 | 招标投标法 或 企业采购制度 | 沿用 P0/P1/P2 既有流程；烟草另参考 `tobacco-industry-notes.md` |

**判定优先级**：看"采购人性质 + 引用的法条"，不看项目内容。政府部门买软件是政府采购，烟草企业买服务是企业采购。
两者兼有（如政府投资的工程总承包）时按 `gov` 处理，因为政采政策性得分项只多不少，漏了才致命。

> ⚠️ 体系判错的代价：判成 `enterprise` 会漏掉价格扣除（最高相当于报价打八折）、漏掉强制采购节能产品（直接无效响应）。**存疑时按 `gov` 走，宁可多做一张核对表。**

## 二、采购方式（五选一，决定流程、术语、报价规则）

| 代码 | 名称 | 识别信号 | 报价轮次 | 中选称谓 |
|---|---|---|---|---|
| `open_tender` | 公开招标 | "公开招标""投标文件""评标委员会""中标" | 一次 | 中标人 |
| `invited_tender` | 邀请招标 | "邀请招标""资格预审后邀请" | 一次 | 中标人 |
| `competitive_consultation` | **竞争性磋商** | "磋商文件""磋商小组""响应文件""最后报价""成交供应商" | **两阶段：首次报价 + 最后报价** | 成交供应商 |
| `competitive_negotiation` | **竞争性谈判** | "谈判文件""谈判小组""最后报价" | **多轮谈判 + 最后报价** | 成交供应商 |
| `inquiry_single` | 询价 / 单一来源 | "询价通知书""单一来源采购""协商" | 一次报价或协商 | 成交供应商 |

## 三、术语映射表（写作时逐词替换，禁止混用）

**这是最容易出硬伤的地方**：模板里的默认词是"投标"体系，用在磋商/谈判项目上属于格式错误，评审可据以判不响应。

| 招标类（`open_tender` / `invited_tender`） | 磋商谈判类（`competitive_consultation` / `competitive_negotiation` / `inquiry_single`） |
|---|---|
| 招标文件 | **磋商文件** / 谈判文件 / 询价通知书 |
| 投标人 | **供应商** |
| 投标文件 | **响应文件** |
| 投标函 | **响应函**（部分文件写"投标（响应）函"，则原样照抄） |
| 投标报价 | **响应报价** / 首次报价、最后报价 |
| 投标保证金 | **保证金**（磋商类常不收，须核对） |
| 投标有效期 | **响应有效期** |
| 评标委员会 | **磋商小组** / 谈判小组 / 询价小组 |
| 评标办法 | **评审办法** / 磋商办法 |
| 中标 / 中标人 | **成交 / 成交供应商** |
| 中标通知书 | **成交通知书** |
| 废标 / 否决投标 | **无效响应** |

**执行规则**：
1. 以招标（磋商）文件**第六章格式原文**为准。官方格式表叫什么就叫什么，一字不改（P0#3 格式克隆已覆盖）。
2. 官方格式未规定的自编文件（如技术方案封面、导航表），按上表统一用词。
3. 阶段6 组装后，用 `check_p0_gates.py` 的术语一致性检查扫描残留错词。

## 四、竞争性磋商 / 谈判专属规则（`competitive_consultation` / `competitive_negotiation`）

### 4.1 两阶段报价——最关键的一条

真实条款（四川某磋商文件 5.3.6）：

> 供应商在**未提高响应文件中承诺的标准**情况下，其**最后报价不得高于**对该项目之前的报价，否则，磋商小组将对其响应文件作**无效处理**。

由此产生三条硬约束，写进 `consultation-strategy.md`：

| # | 约束 | 我方动作 |
|---|---|---|
| 1 | 最后报价 ≤ 首次报价（除非同步提高承诺标准） | **首次报价不能报到地板价**，必须预留最后报价的下调空间 |
| 2 | 最后报价唯一、不高于最高限价、须在规定时间内提交并加盖电子印章 | 到点前完成签章，别卡在最后一分钟 |
| 3 | 提高承诺标准可支撑不降价 | 预先准备"可加码承诺清单"（延长质保、增加驻场人日、增补备件），作为磋商筹码 |

金额修正规则（出错即被动接受修正结果，不确认则无效响应）：
- 大写与小写不一致 → **以大写为准**
- 总价与单价汇总不一致 → **以单价汇总为准**
- 两种以上不一致 → 按上述顺序依次修正

### 4.2 磋商可实质性变动的内容

磋商文件通常单设一章（如"第四章 磋商过程中可实质性变动的内容"），列明**技术要求、服务要求、合同条款**可在磋商中变动。

我方动作：
- 技术方案里对可变动条款**不要写死到不可调整**，预留"可根据采购人最终确认的需求调整"的正当表述（但★实质性要求仍须无偏离响应）
- 在 `consultation-strategy.md` 中预判每条可变动项的**让步底线与加码空间**，磋商现场才有牌打

### 4.3 其他专属条款

| 条款 | 内容 | 我方影响 |
|---|---|---|
| 家数门槛 | 提交最后报价的供应商**不得少于3家**（政府购买服务/科研/科技成果转化类可为2家），不足即终止 | 二次磋商项目（文件名带"(二次)"）说明首次流标，竞争可能不足，中选概率高 |
| 异常低价审查 | 磋商小组可启动异常低价响应审查程序 | 低价策略须准备**成本构成说明**备查 |
| 成交候选排序 | 得分相同→最后报价低者优先→技术指标优→**优先采购产品认证证书数量多者优** | 认证证书数量是并列时的胜负手，尽量多备 |
| 核心产品同品牌 | 提供相同品牌核心产品的不同供应商**按一家计算** | 与代理商/集成商同投时须错开品牌，否则相互挤掉 |

## 五、体系 × 方式 → 阶段裁剪速查

| 阶段 | `gov` 额外动作 | 磋商/谈判类额外动作 |
|---|---|---|
| 0 初始化 | 登记 `--procurement-system gov` | 登记 `--procurement-mode competitive_consultation` |
| 2 解标 | 填 `gov-policy-checklist.md`（价格扣除/强制节能/信用/资格三段式） | 填 `consultation-strategy.md`（两阶段报价+可变动项） |
| 3 资料 | 备中小企业声明函、监狱企业/残疾人证明、节能环标证书、信用截图 | 备"可加码承诺清单"的支撑材料 |
| 4 商务 | 声明函按官方格式**原文照抄填空**，不得改写 | 全文术语切换为响应/供应商/成交 |
| 5 技术 | 强制节能产品须**列明具体产品名称**并附证书 | 可变动条款留调整余地 |
| 6 组装 | 政策性文件单独成节，便于评审定位 | 文件名与封面用"响应文件" |
| 7 审查 | 跑 `check_p0_gates.py` 的 P3 门禁 | 术语一致性检查须零残留 |

## 六、判定流程（阶段2执行）

1. 读采购公告/须知首页 → 判 `procurement_system`（看采购人性质 + 引用法条）
2. 读封面与"须知"标题 → 判 `procurement_mode`（看是"招标文件"还是"磋商/谈判文件"）
3. 两项写入 `project-profile.md` 并**请用户确认**，同步写回 `project-state.json`
4. `gov` → 转 `gov-procurement-policy.md` 建政策核对表
5. 磋商/谈判类 → 建 `consultation-strategy.md`，并在写作前完成术语映射
6. 再按 `project-type-routing.md` 定项目类型与写作骨架

## 七、与既有路由的关系

`procurement-mode-routing.md`（本文，**先执行**）定"法律框架 + 流程 + 术语"；
`project-type-routing.md`（**后执行**）定"写什么内容、技术骨架多厚"。

两者正交：政府采购的运维服务项目 = `gov` + `open_tender` + `service_ops`；
烟草企业的软硬改造项目 = `enterprise` + `open_tender` + `hybrid_retrofit`。
